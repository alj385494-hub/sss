# SQL 注入判定式确认

> 扫描器报的不算，**你能用差分证明的才算**。
> 而且要分清两档：能注入（低）与能取数（高）。

## 一、先找落点

| 高嫌疑参数 | 原因 |
|---|---|
| `id=1`、`page`、`size`、`sort`、`order` | 数字/排序直接拼进 SQL |
| `name=`、`keyword=`、`search=` | 模糊查询拼接 |
| `where=`、`filter=`、`json=` | 结构化查询参数 |
| 报错页含 `SQL syntax`、`ORA-`、`You have an error` | 已确认有 SQL 错误外泄 |

## 二、三种差分确认法

### 1. 布尔差分（最安全）

```bash
# 真条件
curl -s "https://target/item?id=1 AND 1=1"
# 假条件
curl -s "https://target/item?id=1 AND 1=2"
```
**判据**：两个响应在**长度/内容/状态码**上有稳定差异（差 1 字节不算，要多跑几次确认）。

### 2. 时间差分（盲注）

```bash
# 正常
time curl -s "https://target/item?id=1"
# 加延时（MySQL）
time curl -s "https://target/item?id=1 AND SLEEP(3)"
```
**判据**：响应时间差 ≥ 2.5 秒，且可重复 2 次。

### 3. 报错差分

```bash
curl -s "https://target/item?id=1'"
```
**判据**：出现数据库特有报错（`SQL syntax`、`XPATH`、`ORA-01756`、`SQLite3::`）→ 确认注入点，且泄露了 DB 类型。

## 三、证明"能取数"（危害升级）

确认可注入后，**只取证明所需最小信息**：

| 要证明的 | 最小动作 |
|---|---|
| 库名 | `AND 1=2 UNION SELECT database()`（或对应方言） |
| 表名 | 只取 1–2 个表名（`information_schema.tables` 限 1 条） |
| 字段 | 取 1 个表的字段名 |
| 数据量 | 取 `COUNT(*)` 而不是拉数据 |
| 样本 | 1–2 行，敏感字段脱敏 |

**绝对禁止**：`sqlmap --dump` 全库、批量导出用户表、读取 `user`/`password` 明文表。

## 四、判定标准

| 结果 | 定级方向 |
|---|---|
| 确认可注入 + 能取库名/表名 | ✅ 中（有数据访问证明） |
| 确认可注入 + 能读到用户表数据 | ✅ 高（说明是"可批量盗取"） |
| 只有报错泄露 DB 类型，无法注入 | ❌ 不算（信息泄露级） |
| 布尔差 1 字节、时间差 0.3 秒 | ❌ 不稳定，不算 |

## 五、证据要求

1. 真/假两个请求 + 响应（长度/状态/耗时对比表）
2. 时间注入：两次测量耗时（需可重复）
3. 取数证明：库名/表名/COUNT 的响应片段
4. **说明 WAF 情况**：是否被拦、用什么绕过（若无法说明利用方法会被降级）

## 六、失败判据

- 真/假条件响应完全一致 → 无注入
- 时间注入耗时波动大（无规律）→ 无法证明
- WAF 拦掉所有 payload 且无绕过 → 记录后放弃
- 参数被强类型/白名单处理 → 放弃

## 七、边界

- **取证式读取**：只取 1–2 条样本证明可达，不批量导出
- 不用 `SLEEP` 超过 5 秒（避免拖慢业务）
- 不写文件（`INTO OUTFILE`）、不调系统命令（`xp_cmdshell`）
- 不做堆叠查询测试（可能改数据）

## 八、常见坑

| 坑 | 说明 |
|---|---|
| 只看一次响应差异 | 动态页面本来就波动，必须重复验证 |
| 用 sqlmap 一把梭 | 量大、易触发告警，且结果难对应到具体参数 |
| 忽略 URL 编码 | `AND` 前后要编码/空格处理 |
| 把报错当注入 | 报错只说明错误外泄，需差分确认 |
