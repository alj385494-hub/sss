# 组织画像

> 打不动主站时，往往因为**没看清这是谁**。组织画像能指出三条侧路：供应商、员工、代码托管。

## 一、五个维度

### 1. 技术栈与供应商（最实用）

| 来源 | 得到什么 |
|---|---|
| 页脚"技术支持：XXX" | **系统供应商**（往往一套系统多家单位用） |
| 静态资源域名 | CDN/云厂商、对象存储 |
| 登录页版权注释 | 产品名与版本 |
| 招聘 JD | 用的技术栈与内部系统名 |
| 采购/招标公告 | 采购了什么系统（含型号/版本） |

**为什么最实用**：供应商可能服务多家同行 → **一次挖到的方法可复用到同类单位**（但注意：不同单位要分别测，不能一洞多投）。

### 2. 员工与组织架构

| 来源 | 用途 |
|---|---|
| 官网"组织机构"页 | 部门名 → 子域与系统命名规律 |
| 新闻/通知（含联系人） | 员工姓名 + 邮箱格式 |
| 邮箱格式推断 | `zhangsan@` / `zhang.san@` / `zs@` → 账号枚举方向 |
| 招聘页 | 团队规模、技术负责人 |

> ⚠️ 员工个人信息只用于**推账号格式**，不在报告里列人名清单。

### 3. 代码托管与 CI

| 检查 | 方法 |
|---|---|
| GitHub/Gitee 组织 | 搜单位名、缩写、产品名 |
| 仓库列表 | 有无系统源码、配置样例、CI 文件 |
| CI 配置 | `.github/workflows`、`.gitlab-ci.yml` 里的 secrets 引用 |
| 贡献者 | 内部员工账号（后续可看其个人仓库） |

### 4. 云与网络边界

| 检查 | 方法 |
|---|---|
| DNS 服务商 | `dig NS` |
| CDN/WAF 厂商 | 响应头 `Server`、`X-Cache`、`Via` |
| 云厂商 | IP 归属（`whois`/`ipinfo`） |
| 邮件服务 | `dig MX`、SPF 记录里的第三方 |
| IPv6 | AAAA 记录是否独立段 |

### 5. 历史与变更

| 检查 | 方法 |
|---|---|
| Wayback Machine | 老版本页面 → 老接口、老后台入口 |
| 证书透明度（CT） | 历史子域（可能已下线但解析仍在） |
| 备案变更 | 主体是否变更过 |

## 二、产出：一页画像

```markdown
## 组织画像
- 性质：高校 / 企业 / 事业单位（据 ICP 与官网）
- 主系统供应商：XXX（页脚技术支持）
- 身份系统：CAS / Shibboleth / 自研（据 auth 子域）
- 云与 CDN：阿里云 + 某 CDN
- 代码托管：GitHub 组织（N 仓库，无敏感内容）
- 邮箱格式：姓+名@域（据通知页）
- 历史线索：Wayback 有 2019 版后台入口 /oldadmin
```

## 三、判定标准

| 产出 | 价值 |
|---|---|
| 识别出供应商且是通用产品 | ✅ 高（决定打法：产品型 vs 定制型） |
| 找到代码托管且有内容 | ✅ 高（转 `github-secret-hunting`） |
| 找到历史入口 | ✅ 中（常无鉴权） |
| 只有公开介绍页 | ⚠️ 低 |

## 四、失败判据

- 官网只有一张图片，无任何组织信息 → 放弃画像，直接打点
- 代码托管搜不到 → 转供应商/历史线索

## 五、边界（红线）

- **只收集公开信息**，不买数据、不用社工库
- 员工个人信息：只推**邮箱格式**，不整理人名清单、不用于钓鱼
- 不做假冒身份接触（社会工程不在本技能范围）

## 六、常见坑

| 坑 | 说明 |
|---|---|
| 忽略页脚"技术支持" | 这是判断"产品型"最直接的证据 |
| 只看官网不看招聘 | 招聘 JD 里系统名最全 |
| 不做历史快照 | 老后台入口常还活着 |
| 把供应商的系统当目标自建 | 平台对"厂商通用产品"有独立判定口径，要看清楚 |
