# 结项反思与技能进化

> 技能不是写完就完了。**没被用过 = 没写；用过但没改 = 不会长**。
> 本技能定义两件事：**怎么证明技能有效**、**怎么让技能进化**。

## 一、收口后必做三件事（缺一不可）

| # | 动作 | 产出 |
|---|---|---|
| 1 | **技能实测验证** | 证明技能被加载、被判据指导过、避免了哪些误判 |
| 2 | **卡点找案例** | 每个"没挖通/卡住"的环节，去公开案例里找解法 |
| 3 | **回流技能** | 新解法写成技能或补丁，注明来源与适用条件 |

---

## 二、技能实测验证三法

### 方法 1 · 交叉法（最可靠）：用"不知道该用哪个技能"的执行者

```
1. 起一个 fresh 上下文的执行会话（队友/新卡）
2. prompt 只说任务，**不指定用哪个技能**
3. 看它自己选了哪些、理由是什么
4. 回来核对其行为是否与该技能的方法一致
```

**判据**：
- ✅ 有效：它主动加载了对应技能，且**行为细节与技能一致**（如 vhost 扫描用了 `--resolve` + body md5 + 字典上限）
- ⚠️ 半有效：加载了但没按技能做
- ❌ 无效：没加载，或加载了方法与技能无关

**为什么这是最可靠的**：它同时验证了「会不会被找到」和「照着做有没有用」。

### 方法 2 · 反例法：看技能的判据有没有挡住误判

技能里每一条「判定标准 / 失败判据」，都应该在真实目标上兑现过。

```
查：本次有没有因为这些判据而**放弃**了某个候选？
    放弃的理由是否是技能里写的那一条？
```

**判据**：如果一条技能的判据从头到尾没拦住任何东西，它可能是**空话**，需要重写。

**实战样本**（2026-11 某高校）：
- `vhost-enumeration` 的"先做基线"拦住了把 **112 个 502 默认页误判为站点存在**
- `hardcoded-credential-hunt` 的"算不算漏洞"表拦住了把 **硬编码 AES key** 当高危
- `web-xss` 的"反射型多被忽略"拦住了在反射型上做证据
- `phpinfo-to-rce` 的"单列 phpinfo 是低危"拦住了把 phpinfo 当成果

### 方法 3 · 缺口法：看有没有想用但没有的技能

```
查：本次执行中，有没有出现"我知道该做什么，但没有技能可查"的时刻？
```

**判据**：出现 ≥2 次同类缺口 → 该补一个新技能。

**实战样本**：某轮执行者报告"卡在签名 code 参数" → 补了 `sign-param-reverse`；
"不知道 vhost 怎么判" → 补了 `vhost-enumeration`。

## 三、卡点找案例（本技能的核心要求）

### 什么算"卡点"

| 类型 | 例子 |
|---|---|
| **没挖通** | 找到接口但需要签名、找到后台但进不去、有上传点但传不上 |
| **判不了** | 疑似注入但无法证明、疑似越权但无对照 |
| **放弃了但不确定** | 按失败判据放弃，但心里没底（如"是不是我方法不对"） |

### 怎么找

| 来源 | 检索方式 |
|---|---|
| **漏洞社区**（奇安信攻防社区等） | 用**卡点的特征词**检索：组件名 + 参数名 + 报错原文 |
| 官方文档/SDK | 该接口/组件的官方说明（常直接给出参数定义） |
| CVE/漏洞库 | 组件 + 版本 |
| 对应该产品的开发者论坛 | 报错原文 |

**检索词构造原则**：用**报错原文**与**参数名**，不要用"怎么绕过 XX"这种泛词。

例：
- 卡在 `code值不能为空` → 搜 `"code值不能为空" 签名`、`字段 code 签名 规则`
- 卡在 `next dev` 生产环境 → 搜 `next dev 生产 sourcemap`、`Next.js sourcemap 信息泄露`

### 找到之后怎么用

| 发现 | 动作 |
|---|---|
| 有现成解法（步骤清晰） | **写成技能**（或补进对应技能） |
| 只有零散案例（够不成步骤） | **写进对应技能的「常见形态/实战教训」小节**，标来源 |
| 是通用产品的已知缺陷 | 写进技能并注明"需先查是否已被公开" |
| 与我们的红线冲突（如要爆破） | **记录但不采用**，写清为什么不用 |

**必须标注来源**：技能里每条来自公开案例的内容，写明"参考自 XX（链接）+ 抓取日期"，
便于日后核对时效。

## 四、反思模板（写进 `pipeline-state.md` 末尾）

```markdown
## 结项反思（YYYY-MM-DD）

### 1. 技能使用情况
| 技能 | 是否加载 | 是否按方法执行 | 是否拦住了误判 |
|---|---|---|---|

### 2. 卡点与找案例
| 卡点 | 检索词 | 找到的解法 | 是否采用 | 回流到哪个技能 |
|---|---|---|---|---|

### 3. 本次新增/修改的技能
- 新增：xxx（来源：xxx）
- 修改：xxx 的「判定标准」（原因：xxx）

### 4. 下次同类目标该改什么
- 优先打：xxx
- 别再花时间：xxx
```

## 五、什么时候该改技能（判据）

| 现象 | 该改吗 |
|---|---|
| 同一条判据**连续 2 次**判错 | ✅ 必改 |
| 某个失败判据把**有价值的候选**否掉了 | ✅ 必改（判据过严） |
| 某个"常见形态"在真实目标上**完全不同** | ✅ 补一条实战形态 |
| 只是本次目标特殊（一次性） | ❌ 不改，记进 state 即可 |
| 平台口径变了 | ✅ 改平台层技能 |
| 想加一堆"可能有用"的技巧 | ❌ 不加，等真实需要 |

## 六、边界

- 反思里出现客户敏感信息时，**脱敏后再写**
- 从公开案例学到的内容，**不直接复制原文**（版权），要重写并标来源
- 涉及未授权手法的案例，**只吸收判据与判定方法**，不吸收越界操作

## 七、常见坑

| 坑 | 说明 |
|---|---|
| 只写"本次 0 条"，不写为什么 | 反思的核心是"为什么" |
| 把"没找到"当"不存在" | 要区分"确实没有"与"方法不对" |
| 技能越加越多但不删 | 定期用方法 2 检查哪些判据从没生效过，可能该删/重写 |
| 反思写在对话里不落文件 | 下次没人看得到 |
