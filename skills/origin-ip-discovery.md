# 真实源站发现

> 找到源站的价值：**绕过 CDN 的 WAF**，直接看到应用真实行为。
> 判定关键：**直连该 IP + 正确 Host 头，返回与主站一致的内容**。

## 一、先确认"主站是否真的在 CDN 后"

| 检查 | CDN 特征 |
|---|---|
| 响应头 | `Server: volc-dcdn`/`aliyun`/`cloudflare`/`tencent-cdn`/`Via`/`X-Cache` |
| 多 IP | `dig` 返回 3+ 个 IP，且属不同 C 段 |
| CNAME | 指向 `xxx.cdn.xxx` / `wscdns` / `kunlun` |
| 行为 | 对扫描类请求返回 418/403/JS 挑战 |

## 二、七条路径（按成功率）

### 1. 邮件相关记录（最高频）

```bash
dig +short TXT  <domain>          # SPF 里常有源站 IP
dig +short MX   <domain>          # 邮件服务器常在源站网段
dig +short TXT  _dmarc.<domain>
```
SPF 形如 `v=spf1 ip4:<IP> ip4:<IP> -all` → **ip4 列表就是候选**。

### 2. 非 CDN 子域

```bash
# 逐个解析全部子域，挑出没有 CDN 特征的
for d in $(cat subs.txt); do
  ips=$(dig +short A "$d" | grep -E '^[0-9]+\.')
  hdr=$(curl -sI "https://$d/" 2>/dev/null | grep -i "^server" | head -1)
  echo "$d | $ips | $hdr"
done
```
**规律**：`mail.` `vpn.` `oa.` `git.` `jenkins.` `zabbix.` 常直连源站。

### 3. 历史解析（DNS 历史）

免费途径有限，但可查：
- 公开 DNS 历史站点（如 viewdns、securitytrails 免费额度）
- CT 证书里的 IP（部分证书含 IP SAN）

### 4. 证书透明（CT）

```bash
# 从 CT 拿子域，再逐个解析
curl -s "https://crt.sh/?q=%25.<domain>&output=json" | jq -r '.[].name_value' | sort -u
```

### 5. 邮件头（发一封信看 Received）

若能与目标互通邮件（如注册行为触发的通知邮件），看 `Received:` 链里的内部 IP。
**注意**：需要合法交互，不做社工。

### 6. C 段邻近（谨慎）

已知源站 IP 后，其 `/24` 内可能有其他源站。
**红线**：只做少量探测（≤10 个 IP），不做整段扫描。

### 7. 特征匹配（favicon / 报错页）

```bash
# favicon hash 相同 → 同源
curl -s "https://target/favicon.ico" | md5sum
```
用哈希去搜索同源站点（需第三方数据库）。

## 三、验证（关键一步）

找到候选 IP 后：

```bash
curl -s -k "https://<IP>/" -H "Host: <主域>" -o /tmp/o.html -w "%{http_code} %{size_download}\n"
# 与主站响应对比
curl -s -k "https://<主域>/" -o /tmp/o2.html
diff <(md5sum < /tmp/o.html) <(md5sum < /tmp/o2.html) && echo "一致 → 确认源站"
```

**必做三项**：
1. `Host` 头必须是目标域名（否则 Nginx 返回默认站）
2. `-k` 忽略证书（源站证书常与主站不同）
3. 比对内容长度/关键串

## 四、判定标准

| 结果 | 结论 |
|---|---|
| 直连 IP + Host 头返回与主站一致 | ✅ 确认源站 |
| 直连返回 403/默认页 | ⚠️ 可能只是同 IP 的其他 vhost |
| SPF 里的 IP 与主站内容一致 | ✅ 高可信 |
| 只有 CDN IP | ❌ 未找到 |

## 五、证据要求

1. 发现的路径（如 SPF 记录原文）
2. 直连请求（IP + Host 头）+ 响应
3. 与主站响应的对比（长度/关键串一致）
4. 说明该 IP 归属（whois 简要）

## 六、失败判据

- SPF 里无 ip4 且无独立子域 → 放弃
- 所有候选 IP 直连都返回 CDN 拦截 → 源站可能只允许 CDN 回源
- 证书/IP 线索相互矛盾 → 谨慎，别下结论

## 七、边界

- C 段邻近只做**少量**探测（≤10 个），不做整段扫描
- 不做 DNS 历史付费数据采购
- 不通过社工/钓鱼获取邮件头

## 八、常见坑

| 坑 | 说明 |
|---|---|
| 忘记带 Host 头 | 直接访问 IP 看不到目标站点 |
| 用 HTTP 而非 HTTPS | 源站可能只开 443 |
| 忽略证书不匹配 | 源站证书常只有内网名 |
| 把 CDN 回源 IP 当源站 | 需内容比对确认 |

## 实战教训（2026-11，某高校）

### 1. 先用「四项否定」快速排除 CDN，省掉整类工作

| 检查 | 若全部否 |
|---|---|
| 响应头无 `Via` / `X-Cache` / `X-Served-By` | |
| DNS 只有**单条 A 记录** | → **主站即源站** |
| 无 `CNAME` 记录 | → 不存在"绕 CDN 找源站"这道题 |
| 无 WAF 挑战页（无 418/202/JS 挑战） | |

本轮四项全否，直接得出"主站即源站"结论，**没有去翻历史 DNS/邮件头**，
省掉整个面。**先排除比先尝试更高效。**

### 2. 邮件外包时，SPF 里没有源站 IP

本轮 `SPF=v=spf1 include:spf.mail.qq.com ~all`、`MX=mxbiz1.qq.com`、`DMARC=p=reject`
→ **邮件整包在腾讯**，SPF 里一个 ip4 都没有。

> 所以"从 SPF 找源站"这条**只在邮件自建时有效**；邮件外包时这条路直接跳过。

### 3. 前端变量可能直接暴露 `isCDN`

本轮目标的前端 JS 里有 `isCDN=0` 这类变量 → 比看响应头更直接。
**看前端变量是一种被低估的判据。**

### 4. 后续遇 403 要怀疑应用自身

既然没有 CDN/WAF，"被拦截"就不是网络层问题 → 应转
`bypass-401-403`（应用层规范化差异）而不是继续找源站。

## 四之二、先判断 WAF 在 CDN 还是在内网（**2026-11 实测纠正，必读**）

> 原版假定"找到源站就能绕 WAF"。**实测证明这个假设经常错**：
> 有的目标 **CDN 在外层、WAF 部署在源站前**，源站比 CDN 更严。

### 三步判据

| 步 | 做法 | 结论 |
|---|---|---|
| 1 | **同一路径**分别打 CDN 与源站 | 源站状态码更严（如 CDN=200、源站=510）→ WAF 在源站侧 |
| 2 | 看拦截页里的字段 | 若页面自报 `访问 IP: <源站IP>` → **WAF 就在源站** |
| 3 | 比对正常路径的 body md5 | 一致 → 确实是同一应用（源站成立）；不一致 → 是同 IP 的其他 vhost |

**实测样本**：某医院 `www` → CDN 返回 200/4522B，源站 `<IP>` + Host 返回 **510/5691B**，
拦截页写着 `访问 IP <IP>` → **WAF 在源站**，"绕 WAF"这条路不存在。

### 连带动作（价值反而更高）

既然源站被 WAF 罩住，**去找"没有网关的兄弟主机/子域"**：
- 判断方法：响应头**没有** WAF 特征（该案例里是没有 `Server: core`）
- 它的价值：在它上面做**可信的** 404 判定（源码泄露/目录探测）——因为有 WAF 的站点
  对任何路径都返回拦截页，你得到的"404"不可信，会漏掉真实泄露

> 实测：同一目标上，有 WAF 的站点 16 条泄露路径全返回拦截页；而**无 WAF 的 `new` 子域**
> 同样 16 条返回真 404 → **这个"没有"才是可信的"没有"**。

## 实战教训（2026-11，某地方社区论坛 —— 反向验证："拦截页"不等于"不可测"）

### 5. 410/403 全站拦截 → 先分"应用返回"还是"安全设备返回"，再做同路径双端对比

本案上一轮把 `https://www.<域>/` 返回 **410 Gone / 10925 B** 判成"全站不可测"而整轮放弃。
实际拆开看：

| 观察 | 含义 |
|---|---|
| `Server: Tengine` + `Set-Cookie: acw_tc` / `acw_sc__v2` | 阿里云云盾 WAF（acw = Aliyun Cloud WAF） |
| **HTTPS 全路径 410，但 HTTP 返回 200 + 23682 B（JS 挑战）** | 拦截策略**按协议分档**，不是站点关了 |
| 连 `/static/xxx.css` 都 410 | 拦截粒度是"整个 Host"，与路径无关 → 这里得到的 404 全不可信 |

**同路径双端对比（最有价值的一步）**：CDN 侧 `410/10925` vs 源站 `200/30196（真首页）`，
`/robots.txt` 在源站 200 而 CDN 410 —— 一对比就证明"源站无 WAF、CDN 才是拦截层"。

> 判据速查：**410 + 10925 B + Tengine + acw_* Cookie = 阿里云 WAF 策略阻断页**，不是 4xx 业务错误。
> 反面案例也存在（源站比 CDN 更严），所以**不要假定"源站=能绕"**，一律做双端对比。

### 6. 找到的源站可能只是"占位节点" —— 必须用**深层路径**验证，不能用首页

本案有两个候选 IP 的 `/` 都返回同一份 30196 B 首页：

| 深层路径 | 节点 A | 节点 B |
|---|---|---|
| `/` | 200 30196 | 200 30196 |
| `/read.php?tid=<真实 tid>` | **500 572** | **200 196976** |
| `/admin.php` | 500 572 | **200 5277（后台登录表单）** |

节点 A 只挂了首页（`*.php` 一律 500），是占位/静态节点；节点 B 才是应用服务器。
**验证源站的判据必须落在"需要后端处理的路径"上**（详情页、登录页、后台页），
只看首页会同时误判两台机器。

### 7. 源站只开 80 时，别把"HTTPS 连不上"当成"站点挂了"

本案应用服务器只有 `80/tcp`（443 无监听），且 **HTTP 端口对某些 Host 直接 drop**：
`Host: www` 走 80 返回 `Empty reply from server`，而 `Host: bbs` 走 80 正常 200。
→ 结论：**同一台机器要按 Host × 协议 做矩阵**，单点失败不代表面不存在（本案真实入口是
`http://<IP>/` + `Host: www` 之外的组合）。

> 与"源站自带 WAF"那节合起来就是一条总规则：
> **先判拦截发生在哪一层、再判哪台机器是真应用、最后判哪个 Host×协议组合可用**，三步都过了再下"打不动"的结论。
