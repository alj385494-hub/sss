# 教育行业漏洞口径（EDUSRC）

> **用途**：打高校/教育单位时，先用本文件判断「这个洞在教育行业会怎么被判」。
> **来源**：教育漏洞报告平台（EDUSRC）`https://src.sjtu.edu.cn/introduction/` 官方原文，2026-11-13 抓取全文。
> **重要前提**：**EDUSRC ≠ 补天**。我们最终在补天提交，本文件是**行业参考**——用来预判"教育行业的审核直觉"，
> 不能直接当补天规则用。两平台差异见第六节。

---

## 一、什么时候读

| 时机 | 用途 |
|---|---|
| 判类型后、开始打之前 | 看第二节「优先打什么」，避免把预算花在必被忽略的类型上 |

| 定级时 | 第四节等级定义 + 第六节两平台差异 |
| 写报告时 | 第五节「危害表达」+ 无害化三性 |

## 二、优先打什么（按 EDUSRC 认可度）

| 认可度 | 形态 | 依据 |
|---|---|---|
| **最高** | 直接拿重要服务器权限（RCE / 上传 webshell / 可利用溢出） | 严重 9–10 |
| **高** | **可批量盗取用户身份**（订单遍历、普通系统 SQL 注入） | 高危 7–9 |
| **高** | **严重权限绕过**：绕过认证**直接访问管理后台**、cookie 欺骗 | 高危 7–9 |
| **高** | **运维类未授权**：后台管理员弱口令、**服务未授权访问** | 高危 7–9 |
| **中** | **任意文件操作**：任意文件写/删/下载、**敏感文件读取** | 中危 4–7 |
| **中** | **水平权限绕过**：绕过限制**修改用户资料**、执行用户操作 | 中危 4–7 |
| 低 | 能获取一些数据但不属核心数据；条件严苛；需用户交互（XSS） | 低危 0–4 |

### 高校场景最高命中率的三类（结合实战）

1. **下拉/模糊搜索接口的响应过度** → 前端只显示姓名，后端返回学号/身份证/手机/学院（详见 `target-type-playbook` 的 M7）
2. **绕过认证直接访问后台**（教务/图书馆/OA 的老系统）
3. **服务未授权访问**（Redis/ES/Mongo/未授权管理端）

## 三、【硬门禁】忽略清单 22 项（原文）

> 命中任意一条 → **不提交**。这是 EDUSRC 原文，逐字保留。

| # | 忽略项 | 对我们的含义 |
|---|---|---|
| 1 | 非（不确定）教育相关行业单位 | 归属要先坐实 |
| 2 | 虚假漏洞 | — |
| 3 | 本平台已有其他白帽子提交过的漏洞 | 提交前去重 |
| 4 | 互联网上已被公开的漏洞 | 公开 Nday 无定制分析不值钱 |
| 5 | 提交到本平台后又提交到其他平台的漏洞 | 别多平台重复投 |
| 6 | 没有链接、截图、利用方法等漏洞详情不详细的漏洞 | 四件套要齐 |
| 7 | **需要登录管理员后台才能触发的漏洞** | 后台类要能在未授权或普通用户态触发 |
| 8 | 需要中间人攻击的漏洞 | — |
| 9 | **反射型 XSS** | 别投入 |
| 10 | **CSRF 漏洞** | 别投入 |
| 11 | 钓鱼漏洞 | — |
| 12 | 无敏感信息的 JSON Hijacking | — |
| 13 | **扫描器取得结果，但白帽子无法提供利用方法的漏洞** | nuclei 命中后必须能手工复现 |
| 14 | **无意义的源码泄露、内网 IP、域名泄露、路径泄露** | ⚠️ sourcemap / `.js.map` / DNS 内网 IP / 路径泄露 **全在此列** |
| 15 | 拒绝服务漏洞 | — |
| 16 | 点击劫持 | — |
| 17 | 短信轰炸、邮件轰炸 | — |
| 18 | **CORS** | ⚠️ 别交 |
| 19 | 既没有系统管理权限，也获取不到敏感信息的**弱口令** | 弱口令门槛很高 |
| 20 | **用户名枚举** | ⚠️ Azure AD 枚举类在此列 |
| 21 | pdfxss | — |
| 22 | **URL 跳转** | ⚠️ 开放重定向在此列 |
| — | 不能注册管理员用户的用户注册问题 | — |

## 四、降级清单 7 项（原文，"酌情降低等级"）

| 降级原因 | 我们的对策 |
|---|---|
| 漏洞真实存在，但因 WAF 等问题**无法说明利用方法** | 复现必须跑通，被 WAF 拦就换路径 |
| 提交前单位已知晓但暂未修复 | 越新越好 |
| 触发需要一定条件，具有**偶然性** | 对应 rejection-cases 的 R5 |
| **同一单位多处相似漏洞** | 同单位多条要合并或挑最强的一条 |
| **恶意夸大漏洞危害** | ⚠️ 对应 R2：禁写"可进一步/理论上" |
| 非同一单位但利用方式相似 | 别把同一手法套多个单位交 |
| 已公开利用方式的通用型漏洞 | 要加定制化分析 |

## 五、无害化验证（三性，官方原文要点）

> 这段可以直接引用到报告/合规说明里——它是**官方依据**，比我们自定的纪律更权威。

| 维度 | 官方要求 |
|---|---|
| **机密性** | 验证越权/非授权时，**不应再获取和留存**用户信息和文件信息；获得库表名证明后不应再查详细数据；获得主机权限后不应再取业务数据；**禁止用当前主机作跳板对内网扫描测试** |
| **可用性** | 充分估计安全冗余，**不进行可能导致瘫痪的大流量/大规模扫描**；禁止 DoS 用例；禁止可能导致业务逻辑扰动、用户财产损失的用例 |
| **完整性** | 获得后台操作权限后**不应再编辑/增删/篡改**；获得 DB/主机高权后不应改文件数据；上传可解析文件后**不应驻留控制性程序** |

**其它硬要求**：测试后及时删除遗留文件与权限（Webshell 等）；涉及金钱的测试须在报告写明测试账户；严禁虚假漏洞；不向无关人员泄露。

## 六、两平台口径差异（**最容易踩的坑**）

| 漏洞形态 | **EDUSRC** | **补天** | 提交时怎么选口径 |
|---|---|---|---|
| 绕过认证直接访问管理后台 | **高危 7–9** | 中危（口径第 5 类） | 投补天按补天写，别用 EDUSRC 的高危说法 |
| 可批量盗取用户身份 / 订单遍历 | **高危** | 未单列 | 强调"能读到大量用户数据" |
| 服务未授权访问（运维类） | **高危** | 归信息泄露/配置 | 强调实际能取到什么 |
| 任意文件读取/下载 | **中危** | 归信息泄露 | — |
| 水平权限绕过（改他人资料） | **中危** | 归逻辑漏洞 | — |
| 用户名枚举 | **忽略** | 未明列，但实际易被驳 | **两边都不交** |
| URL 跳转 / CORS / 反射 XSS | **忽略** | 多归忽略项 | **两边都不交** |

**结论**：EDUSRC 的高危项在补天可能只算中危；EDUSRC 明确忽略的项（用户名枚举、URL 跳转、CORS、源码/路径/内网 IP 泄露）在补天也基本没搞头 → **这些可以直接不投入**。

## 七、奖励范围（判断值不值得打）

接收：
- 教育部、人力资源和社会保障部、中国科学院
- 各省/自治区教育厅、直辖市教委、各级教育局；各省人社厅/局
- 上述部门主管的**学校、技校**
- 中科院所属各单位（中心、研究所）
- **教育相关软件**

范围外无奖励。

## 八、维护

1. 每次打高校/教育单位结束，把"哪些候选因哪条忽略项被筛掉"记进案例（可回流 `butian-rejection-cases`）。
2. 若 EDUSRC 规则更新（`/announcement/` 有公告），重抓 `introduction` 并 diff 本文件。
3. 本文件**只放教育行业口径**，通用提交规则在 `butian-submit`，真实裁决在 `butian-rejection-cases`。
