# 补天平台漏洞提交规范

> 本技能是**提交环节**的规则集。产出漏洞、拿证据由其他技能负责；这里只解决"怎么组织材料才能过审"。
> **铁律：AI 不得自主提交。** 所有报告必须由上报者本人逐条核验数值、截图、PoC 后才能提交——平台对真实性负完全责任的是人，不是工具。

---

## 零、先记住五条

1. **报告里每个数值都必须来自你当次实测**，不是记忆、不是推断、不是上次的结果。
2. **两类截图缺一不可**：漏洞完整复现过程 + 厂商归属证明。缺归属证明是最常见驳回原因。
3. **合规红线一旦踩中，报告作废还可能封号**（见第二节）。
4. **去 AI 化：复现全程走软件**——报告里的复现步骤必须是「打开哪个软件、点哪里、看到什么」，
   **不得以 PowerShell / curl / python 命令作为复现步骤，不得用命令行截图作证据**（见第四节之四）。
5. **报告开头必须给出「标题 + 类型 + 等级 + 简要描述」速填区**——补天表单有独立输入框，
   简要描述是审核第一眼看的内容，150–300 字、一段到底、含机制与危害（见第五节）。

## 一、平台 4 项硬性要求（表单原文口径）

| # | 要求 | 交付物 |
|---|---|---|
| 1 | 详细描述漏洞的测试或复现过程以及影响范围 | 报告「一、」章节：分步骤复现 + 影响范围表 |
| 2 | 附相关证明截图（**本地上传，勿复制粘贴**）<br>①漏洞完整复现过程截图 ②厂商归属证明截图<br>未提供可能被驳回，可通过附件补充视频 | 两类截图**分组上传** |
| 3 | 提供漏洞利用过程使用到的组件（组态软件、远程调试工具等）下载链接，或附件上传 | 报告「三、」表格 + 官方链接 |
| 4 | 给出漏洞 PoC 或 Exploit，语言不限；思路清晰、可阅读性高、易于复现 | 报告「四、」完整代码 + 命令行 + 判定标准 |

### 报告六要素（每条漏洞必须齐）

`漏洞 URL` / `漏洞所在功能点` / `漏洞验证过程` / `完整数据包及 POC` / `漏洞验证证明` / `危害证明`

> 平台明确要求：不得用 AI 生成的通用模板内容代替真实测试过程。

## 一点五、表单「漏洞类型」下拉实际选项（以此为准）

> 提交表单的类型是**固定下拉**，不是自由填写。平台《收录范围》里写的 10 类与表单下拉**不一致**，
> **以表单下拉为准**——填错类型会被分流到错误审核队列，直接影响通过率。

### 下拉实际 13 项（实测截图确认，2026-11-11）

```
XSS
配置错误
弱口令
入侵事件
疑似被黑
文件上传
信息泄露
存在后门
逻辑漏洞
代码执行
命令执行
SQL注入
解析漏洞
```

### 关键差异（最容易踩的坑）

| 收录范围写的 | 表单里有吗 | 该怎么办 |
|---|---|---|
| **权限绕过 / 越权 / 未授权访问** | ❌ **没有** | 读数据型 → 选「**信息泄露**」；能执行操作/改数据型 → 选「**逻辑漏洞**」 |
| **文件包含 / 任意文件操作** | ❌ 没有独立项 | 读文件 → 「信息泄露」；写/删/上传 → 「**文件上传**」 |
| — | ✅ 有「**配置错误**」 | phpinfo、默认页、目录列举、版本泄露、调试开关 → 选这个（注意：这类本身是平台忽略项） |
| — | ✅ 有「**入侵事件**」「**疑似被黑**」 | 域名被劫持/挂博彩/被植入黑页 → 选这两个，属于事件型 |
| — | ✅ 有「**解析漏洞**」 | 上传文件名解析（IIS/Apache/Nginx 解析缺陷）单独归类 |

### 映射表（常见发现 → 下拉选择）

| 你的发现 | 选哪个 | 备注 |
|---|---|---|
| 未授权读配置页 / 接口返回业务数据 | **信息泄露** | 最贴切；不要硬找"越权"选项 |
| 未授权可执行操作（改资料、下单、重置他人密码） | **逻辑漏洞** | 越权写操作用这个 |
| 账号可枚举 / 接口泄露账号清单 | **信息泄露** | |
| 验证码不校验 / 登录逻辑缺陷 / 顺序绕过 | **逻辑漏洞** | 认证流程缺陷 |
| phpinfo / 目录列举 / 默认文件 / 版本信息 | **配置错误** | 同时属平台忽略项，别单独交 |
| 命令注入、系统命令执行 | **命令执行** | |
| 任意代码执行、反序列化 RCE、模板注入 | **代码执行** | |
| 上传点可传脚本且可执行 | **文件上传** | |
| 域名被挂博彩/黑页/被劫持 | **疑似被黑** 或 **入侵事件** | 需先分清是自建/出租还是被黑 |
| 服务器被留后门、隐藏账号 | **存在后门** | |

### 报告里怎么写

报告「1.1 漏洞基本信息」和「表单速填区」的**漏洞类型必须用下拉里的原词**，不要写「越权访问」「未授权访问」「权限绕过」这类平台没有的标签。

```markdown
**漏洞类型**：信息泄露        ← 用下拉原词
> 判定口径：按平台中危第 5 类「越权访问—绕过认证访问后台」定级（这是**定级依据**，不是类型）
```

**两个概念要分开写**：
- **漏洞类型** = 表单下拉选项（固定 13 项之一）
- **平台定级依据** = 《收录范围》里的话术（用来解释为什么是中危）

## 二、测试禁止事项（原文，违反封号）

参与测试须遵守以下禁止事项：

1. **禁止任何形式的爆破测试**，包括短信 / 邮箱轰炸、并发提交工单等；
2. **禁止执行恶意消耗系统资源的 SQL 操作**，仅限漏洞验证使用；
3. **禁止暴力调用验证码**；
4. **禁止修改任何生产数据**（更改、删除非测试人员数据、密码；覆盖生产文件数据等）；
5. **禁止保存、下载、外传测试过程中获取的任何敏感数据**，漏洞证明危害即止；
6. **严格管控 AI 权限**，不得完全依赖提示词约束 AI，须限制其操作权限与执行范围；高风险操作必须经过人工确认，**禁止 AI 自主执行**；
7. 白帽子对所提交报告的**真实性和准确性负有完全责任**，无论是否借助 AI 工具，均视为上报者本人行为。

## 三、AI 辅助报告要求（原文）

1. 提交的漏洞报告应基于**白帽子本人真实的安全测试发现**，确保漏洞内容真实、可复现、描述准确；
2. 如使用 AI 工具辅助生成报告内容，上报者须**对报告内容进行人工逐条验证与核实**，确认漏洞真实存在且描述与实际一致后方可提交；
3. **禁止**直接将 AI 生成的、未经人工验证的漏洞报告**批量提交**至平台，包括但不限于使用 AI 工具自动扫描、自动生成漏洞描述并直接上报的行为；
4. 报告须包含**充分的技术细节和有效的复现步骤**，不得以 AI 生成的通用模板内容代替真实测试过程。报告需完整包含：漏洞 URL、漏洞所在功能点、漏洞验证过程、完整数据包及 POC、漏洞验证证明、危害证明；报告中需包含对应的细节截图及文字描述；
5. 遵守《补天平台白帽子行为规范与漏洞提交须知》及《AI 生成漏洞报告提交规范》。

### AI 违规报告处置（原文）

- 累计提交 **超过 3 个** AI 生成且未经人工验证报告 → 平台提醒；
- 累计提交 **超过 5 个** → 视情况**扣除信誉值**，情节严重**封号**。

> **对本技能的直接约束**：本技能只能用来"组织材料"，不能用来"代替实测"。凡是没跑过的请求、没截到的图、没核过的数值，一律不得写进报告。

## 三点五、收录范围与收益自查（先判断值不值得交）

> 依据《漏洞收录范围及奖励标准》。**提交前必须先过这一节**，否则容易白干。

### 3.5.1 三条硬门槛

| 门槛 | 规则 | 影响 |
|---|---|---|
| **IP 漏洞暂不收取** | 必须以**域名 URL** 提交 | 只有裸 IP 的漏洞直接不交 |
| **gov / edu 无权重要求** | 政府、教育单位不看爱站权重 | 学校/政府站可正常提交，不用纠结权重 |
| 收录范围 | 专属SRC、公益SRC、**未注册厂商**（按权重定奖励） | — |

### 3.5.2 关注的漏洞类型（Web）

`XSS` `SQL注入` `命令执行` `代码执行` `文件包含` `任意文件操作` `权限绕过` `逻辑漏洞` `信息泄露` `存在后门`

### 3.5.3 等级判定（平台口径，不是自估）

**高危（4 类）**
1. 直接获取服务器权限：任意命令执行、上传 webshell、任意代码执行
2. 直接导致严重信息泄露：大量个人敏感信息泄露
3. 支付类逻辑漏洞：影响盈利的改金额
4. 能盗取用户身份且影响严重：可获取大量敏感信息或执行命令的 SQL
5. 可直接重置管理员密码且导致大量敏感信息泄露

**中危（7 类）**
1. 能直接盗取用户身份信息：一般 SQL 注入（**需证明可获取库名/用户名**）
2. 相对严重的逻辑漏洞：管理员/普通用户密码重置（但无法导致大量信息泄露）
3. 需交互才能获取身份信息：存储型 XSS
4. 任意文件操作：任意文件读/写/删除/下载
5. **越权访问：绕过认证访问后台、绕过限制修改用户资料、执行用户操作**
6. 比较严重的信息泄露：敏感信息文件泄露（如 DB 连接密码）
7. 弱口令（**不含前台弱口令**）

**低危（2 类）**
1. 普通逻辑漏洞：redis 未授权、heapdump 敏感信息泄露、短信轰炸
2. 需交互才能获取身份信息且有一定利用难度

> 定级还需综合：厂商权重、网站流量、攻击复杂度、对目标的影响、权限需求、影响范围、机密性/完整性。

### 3.5.4 会被忽略或降级的（提交前逐条自查）

| # | 平台明确忽略/降级的情形 | 自查要点 |
|---|---|---|
| 1 | 无实际危害或危害太小：**url跳转、前台个人弱口令、任意用户注册、self-xss、邮箱轰炸、CORS 配置错误、Web 安全配置缺陷或安全加固缺失类** | phpinfo、默认页、版本号泄露、缺安全头 → 大概率不收 |
| 2 | 无法直接利用的数据/信息：**内网信息泄露**、已过期 key | 只泄露内网 IP/域名的不值钱 |
| 3 | 破坏性操作：拒绝服务 | 不做 DoS |
| 4 | 无敏感信息类：已脱敏信息、公开文件、**API 接口泄露但无有效信息** | 无账号/姓名的接口泄露 → 不收 |
| 5 | **同一系统同类型漏洞超过 3 个** | 同一系统同类不超过 3 条，超了不发奖励 |
| 6 | SQL 注入按**接口**算，同一接口多参数算一处 | 别按参数数量刷 |
| 7 | 通用产品漏洞衍生的不同企业事件型漏洞，平台累计收录 >50 个后降为 1KB/个 | 老 Nday 不值钱 |
| 8 | **未经人工验证的 AI 生成漏洞**（多次提交可能封号） | 见第三节 |

### 3.5.5 平台「不关注系统/厂商」名单（关键风险）

平台公告了一份「不再关注」的系统/厂商名单（理由：漏洞过多、长期不修复）。
**若目标系统在该名单内，其漏洞存在被忽略或大幅降价的风险。**

对本次常见目标的抽查结果（**不是穷举，提交前应去原文核对**）：

| 目标系统 | 是否在名单 | 备注 |
|---|---|---|
| **QiBoCMS（齐博CMS）** | ⚠️ **在列** | 使用该 CMS 的站点漏洞可能被忽略，提交前要评估 |
| 泛微 OA | ⚠️ 在列 | |
| 正方教务系统 | ⚠️ 在列 | 高校常见 |
| 强智科技 | ⚠️ 在列 | 高校教务常见 |
| 万户网络 | ⚠️ 在列 | |
| 通达 | ⚠️ 在列 | |
| 青果软件 | ⚠️ 在列 | 高校教务常见 |
| 江苏汇文软件 / 南京先极 / 南京苏亚星 | ⚠️ 在列 | 高校图书馆/教务常见 |
| 极限OA / 金和 / 科瑞OA / 海天OA | ⚠️ 在列 | |

> **判读要点**：名单针对的是「系统/产品」层面的通用问题。
> 若提交的是**事件型漏洞**（某单位自己部署的实例），仍可能被收录，但**优先选不在名单里的目标**更稳。
> **高校常见 CMS/教务系统大量在名单内 —— 打 edu 靶标时要特别留意这一条。**

### 3.5.6 奖励量级（事件漏洞，按厂商权重）

| 厂商档 | 低危 | 中危 | 高危 |
|---|---|---|---|
| 相对较小 | 1–2 KB | 2–3 KB | 4–6 KB 或 ¥100–200 |
| 中大型（运营商、高权重站） | 2–4 KB | 4–6 KB | 8–12 KB 或 ¥100–300 |
| 大厂（BAT 级） | 3–6 KB | 6–9 KB | 12–18 KB 或 ¥200–600 |
| 权重 0 | 100–200 荣誉币 | 200–300 | 400–600 |

- 奖励形式：现金 / KB / 荣誉（rank、榜单）—— **单一奖励，不叠加**
- **每月仅前 100 个有效漏洞发放奖励**，超出无奖励
- 通用漏洞（第三方软件本身）奖励另算：重点应用 ¥1000–10000，小众厂商 ¥50–500
  - 通用漏洞要求：能下载源码，或**至少提供 10 个以上受影响案例**
  - 基于后台登录的漏洞、弱口令，通用类型一般**不收**

### 3.5.7 提交前收益自查（4 问）

```
Q1 是域名 URL 还是裸 IP？          → 裸 IP 不交
Q2 属于 3.5.2 的哪一类？           → 不在 10 类里就不交
Q3 命中 3.5.4 哪条忽略规则？        → 命中就别花时间
Q4 目标系统在 3.5.5 不关注名单吗？  → 在列则降优先级，或改选其它目标
```

四问都过了，再按 3.5.3 定级、按 3.5.6 估收益，决定投入多少时间。

## 三点六、工具链流转（软件调用链）—— 报告必含章节

> **目的**：证明漏洞是**真人按流程一步步挖出来的**，而不是 AI 凭空生成的。
> 审核看这一节能判断「这人真的做过信息收集 → 资产梳理 → 漏洞发现 → 验证」的全过程。

### 三点六之一、必须写什么

报告里必须有「**工具链流转**」表，形式是一个**首尾相连的链条**：

```
阶段 → 用了什么软件 → 输入（从上一步来） → 产出结果（具体数字） → 产出交给谁继续用
```

**每一行必须齐四项**：

| 字段 | 要求 |
|---|---|
| 阶段 | 信息收集 / 资产梳理 / 指纹识别 / 目录枚举 / 漏洞扫描 / 人工验证 / 抓包分析 / 复现取证 |
| 软件 | **具体软件名 + 版本**（如 `httpx 1.6.10`、`Burp Suite Community 2026.8`、`Firefox 128 ESR`） |
| 产出结果 | **具体数字**（发现 N 个子域 / N 个存活 / N 个敏感路径），不能写「发现一些」 |
| 产出用于 | 明确指出交给**下一行哪个软件**、用来干什么 |

### 三点六之二、标准表格式

```markdown
## 1.0 从信息收集到漏洞确认的工具链流转

| # | 阶段 | 使用的软件（版本） | 输入（来源） | 产出结果 | 产出用于 |
|---|---|---|---|---|---|
| 1 | 子域枚举 | <软件> <版本> | 靶标主域 `example.edu.cn` | 发现 **N** 个子域名 | 交给 ② 做存活探测 |
| 2 | 存活与指纹 | <软件> <版本> | ①的 N 个子域 | **N** 个返回 200；识别出 <指纹> | 交给 ③ 做目录枚举 |
| 3 | 目录枚举 | <软件> <版本> | ②的存活 URL | 发现 **N** 个敏感路径，含 `<关键路径>` | 交给 ④ 人工验证 |
| 4 | 人工验证 | `Firefox 128 ESR` | ③的敏感路径清单 | 确认 **N** 个页面未授权可读 | 交给 ⑤ 分析请求 |
| 5 | 抓包分析 | `Burp Suite Community` | ④中可交互的页面 | 发现 <机制缺陷> | 交给 ⑥ 构造请求 |
| 6 | 复现取证 | `Burp Repeater` | ⑤的缺陷点 | 确认漏洞并截图 N 张 | 形成本报告 |

**本漏洞的定位路径**：

```

### 三点六之三、写作要点

| 要点 | 说明 |
|---|---|
| **首尾相连** | 每一行的「产出用于」必须能对上下一行的「输入」，不能断链 |
| **数字要真** | 数量必须是你当次实际的统计值，不能编；记不清就回去数 |
| **软件要具体** | 写版本号；只写「扫描器」「浏览器」不算合格 |
| **只写导向本漏洞的关键节点** | 不要把全部扫描动作罗列成流水账 |
| **数量级要克制** | 写「发现 28 个子域」可以；写「爆破 14000 条目录字典」「跑了 14000 个模板」会让人认为你在无差别扫描，反而减分 |
| **不贴命令、不贴终端截图** | 这一节是**流程说明**，不是复现步骤；复现步骤仍必须是 GUI 操作（见四之四） |

| 红线 | 具体含义 |
|---|---|
| 不爆破 | 不加载字典、不批量提交口令、不做密码喷洒、不并发轰炸 |

- ❌ 不得出现：`字典` `爆破` `尝试 N 个口令` `密码喷洒` `弱口令尝试` `撞库`

### 四之四、去 AI 化交付要求（复现一律软件操作）

> 平台明确「去 AI 化」：报告必须体现**真人手工测试**的过程痕迹。
> 命令行脚本 + 终端截图 = 最像 AI 自动跑批的证据，**一律不用**。

#### 硬性要求

| 项 | 要求 |
|---|---|
| **复现环境** | **优先在 Kali 虚拟机内完成全部操作**（浏览器 / Burp / 数据库客户端都在 Kali 里）。宿主机只在 Kali 确实不可用时兜底，并在报告里写明原因 |
| **复现步骤** | 必须是 GUI 操作序列：「打开 X 软件 → 输入地址 → 点击 Y → 看到 Z」，**细到可直接照做**（含快捷键、菜单路径、字段值） |
| **复现截图** | 必须是**软件界面**（浏览器窗口含地址栏 / Burp 面板 / 数据库客户端），**不得用终端截图** |
| **软件面板截图数量** | 每条漏洞至少 1 张「请求+响应同屏」的 Burp/Yakit 面板图；只给网页截图会被判「未展示验证过程」 |
| **报告正文** | 不得出现 PowerShell、cmd、curl、python 命令作为「复现步骤」 |
| **PoC** | 仍按表单第 4 项作为**附件**提供，但定位是「可复现性证明」，**不替代手工复现步骤** |

#### 复现环境写实原则

报告里的「复现环境」必须与实际操作一致，**不能为了统一而写成没用过的环境**。

| 情况 | 怎么写 |
|---|---|
| 全部在 Kali 完成 | `操作系统：Kali Linux 2026.x` |
| 个别截图因目标兼容性在宿主机完成 | 写主环境 + 一行说明，例如：`注：该站点对 Kali 内浏览器的 .nsf 请求会重置连接（命令行请求正常），故该组界面截图在 Windows 11 的 Chrome 完成，网络行为一致` |
| 绝对不要 | 把 Windows 上截的图写成「Kali 中完成」——违反真实性要求 |

#### 各漏洞类型对应的软件

| 漏洞类型 | 用什么软件复现 |
|---|---|
| Web 页面未授权/信息泄露 | 浏览器（Chrome / Firefox），截图带地址栏 |

| 无痕/未登录态 | 浏览器无痕/隐私窗口（截图要能看到「无痕」标识） |
| 数据库/接口 | 对应 GUI 客户端，不用命令行 |

## 十一、常见驳回原因与规避

| # | 驳回原因 | 规避 |
|---|---|---|
| 1 | 缺厂商归属证明 | 每份报告单列一章，至少 2 张图 |
| 2 | 状态码/数值与实测不符 | 提交前重测，逐项比对 |
| 3 | 报告含爆破描述 | 全篇删除，只写机制缺陷 |
| 4 | 截图是粘贴的 | 明确本地上传 |
| 5 | AI 生成未人工验证 | 每条数值逐项核对并留痕 |
| 6 | 截图截到终端/无关窗口 | 按窗口标题精确截取 |
| 7 | 页面 JS 跳转导致证据失效 | 用 `view-source:` 取原始源码 |
| 8 | 目标已修复仍提交 | 提交前跑验证脚本确认仍存在 |
| 9 | 用通用模板代替真实过程 | 过程必须写本次实际命令与回显 |
| 10 | 同系统多漏洞被判重复 | 明确区分 URL/功能点/漏洞类型，说明差异 |

## 十二、提交 SOP（8 步）

```
1. 漏洞确认   → 跑验证脚本，确认漏洞仍存在（避免提交已修复的）
2. 复现截图   → 浏览器/Burp 按窗口精确截取，逐张自查
3. 归属证明   → 4 类证据取 2–3 张
4. 写报告     → 4+2 段式模板，过程写实际命令与回显
5. 写 PoC     → 零依赖 + 判定标准 + 合规声明
6. 数值核对   → 报告数值 vs 当次实测逐项比对
7. 生成清单   → 每条漏洞列出「报告/复现截图/归属截图/PoC」四件套
8. 人工复核后提交 → 打勾记录，保留驳回理由以便整改
```

### 第 7 步的清单要素

每条漏洞一行，必须齐四件套：

| 报告文件 | 复现截图 | 归属证明截图 | PoC 附件 |
|---|---|---|---|

外加：等级、URL、合规要点、是否已提交。

## 十三、提交顺序（按「过审几率 × 危害」排序）

### 排序公式

```
综合分 = 提交几率(1-5) × 2 + 危害程度(1-5)
```

**提交几率权重加倍**：被驳回的报告收益为 0，所以「能过」比「危害大」更重要。

### 两个维度的打分要点

**提交几率（1-5）**——看这条能不能过审：

| 分 | 判断 |
|---|---|
| 5 | 完全命中平台中危/高危口径**原文**（如「越权访问—绕过认证访问后台」），且证据链完整（有对照组/无痕/双请求对比） |
| 4 | 命中平台口径，但审核可能低估（需要额外解释技术栈） |
| 3 | 类型归类不明确，或目标/产品在「不关注名单」，或可能落入忽略规则 |
| 2 | 明显命中忽略规则（Web 安全配置缺陷、无敏感信息泄露等） |
| 1 | 平台明确不收（裸 IP、已公开、无实际危害） |

**危害程度（1-5）**——看这条影响多大：

| 分 | 判断 |
|---|---|
| 5 | 涉及全校/全体用户的账号、身份、敏感数据 |
| 4 | 涉及服务器级配置、可进一步打开其他库/服务 |
| 3 | 涉及单个业务系统的配置、策略、功能边界 |
| 2 | 单个页面/接口的少量信息 |
| 1 | 几乎无实际影响 |

### 排序后的执行原则

1. **先交综合分最高的**——优先拿下确定能过的。
2. **忽略规则内的漏洞不单独交**，改为并入高分报告作「危害加剧证据」。
3. 同分时：证据链更完整（有对照组）的优先。
4. 每月只有前 100 个有效漏洞计奖励，**不要把额度浪费在被忽略的类型上**。

### 示例（某省属师范高校 5 条）

| 漏洞 | 几率 | 危害 | 综合 | 决定 |
|---|---|---|---|---|
| 选课系统配置页未授权 | 5 | 3 | **13** | 第 1 个交 |
| Domino 配置库未授权 | 4 | 4 | **12** | 第 2 个交 |
| Azure AD 账号可枚举 | 3 | 5 | **11** | 第 3 个交 |
| 齐博CMS 验证码未校验 | 3 | 3 | **9** | 第 4 个交 |
| phpinfo 环境暴露 | 2 | 2 | **6** | 不单独交，并入齐博CMS 报告 |

## 十四、公开可核查性

报告中出现的每个外部地址/接口，都应能被审核人员独立复现：

- URL 必须精确（含端口、路径、**注意双斜杠等非常规写法**）
- 请求必须可重放（完整请求行 + 必要头部 + body）
- 响应特征要写明（状态码 + 长度 + 关键字段），便于比对
