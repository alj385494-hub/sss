# 业务逻辑漏洞

> 技术层面全对，但**业务规则**可以被绕过——这类漏洞平台认可度高，因为没有 WAF 能拦。

## 一、按业务类型找点

### 1. 验证码 / 短信

| 测试点 | 判据 |
|---|---|
| 验证码是否与手机号绑定 | 用 A 手机号收到的码，提交时改成 B 手机号 |
| 验证码是否一次性 | 同一码用两次 |
| 验证码是否与场景绑定 | 注册场景的码拿去重置密码 |
| 是否有频控 | 连续请求 3 次看是否被限（**不做轰炸**） |
| 前端是否校验 | 抓包看校验是否只在 JS 里 |

**最高价值**：验证码与手机号/场景**未绑定** → 可越权登录他人账号。

### 2. 注册 / 登录

| 测试点 | 判据 |
|---|---|
| 重复注册 | 同一手机号注册两次是否覆盖原账号 |
| 注册字段越权 | 注册时能否指定 `role`/`type`/`isAdmin` |
| 密码重置 | 重置凭证是否与用户绑定 |
| 登录后身份 | 登录响应里的 `role` 能否被客户端改 |

### 3. 支付 / 金额

| 测试点 | 判据 |
|---|---|
| 金额篡改 | 前端传 `amount`/`price`，改成 0.01 是否被服务端接受 |
| 数量为负 | `quantity=-1` 是否导致余额增加 |
| 币种/单位 | 小数位、积分抵扣换算 |
| 重复使用订单 | 同一订单号支付两次 |

**纪律**：**只验证到"服务端接受异常值"为止，绝不完成真实支付**。用测试商品/最小金额。

### 4. 优惠券 / 积分

| 测试点 | 判据 |
|---|---|
| 重复领取 | 同一账号/设备领多次 |
| 越权使用 | 用他人券 ID |
| 叠加使用 | 多张券同时生效 |
| 过期后使用 | 改客户端时间无效（服务端校验） |

### 5. 审批流 / 状态机

| 测试点 | 判据 |
|---|---|
| 跳过中间状态 | 直接从"待审"跳到"已通过" |
| 越级审批 | 低权限调用审批接口 |
| 自己审自己 | 提交人 = 审批人 |
| 撤回后重放 | 撤回的申请再次提交 |

### 6. 并发竞争

| 测试点 | 判据 |
|---|---|
| 同一资源并发扣减 | 并发 2–5 个请求，看是否超扣/超领 |
| 并发领券 | 一次并发领多张 |

**纪律**：并发数 ≤5，只做一次，不反复压。

## 二、执行原则

1. **先理解业务**：把正常流程走一遍，记录每步的请求
2. **一次只改一个变量**：金额、数量、id、状态
3. **保留对照组**：正常请求 vs 篡改请求的响应对比
4. **不产生真实后果**：不下真单、不真扣款、不真发短信给他人

## 三、判定标准

| 现象 | 结论 |
|---|---|
| 服务端接受篡改值并返回成功 | ✅ 逻辑漏洞（需说明会造成什么实际结果） |
| 前端改了但服务端纠正 | ❌ 不算 |
| 返回错误但错误信息暴露内部逻辑 | ⚠️ 最多是信息泄露 |

**写危害时必须落到"实际后果"**：
- ❌ "可以篡改金额"（这是过程）
- ✅ "提交 0.01 元订单，服务端返回支付成功，实际应付 199 元"（这是后果）

## 四、证据要求

1. 正常流程的完整请求链（几步）
2. 篡改点的请求 + 响应（证明服务端接受了异常值）
3. **后果证明**：订单状态/余额变化/权限变化的截图
4. 说明测试用的测试账号与测试商品（涉及金额时必须写）

## 五、失败判据

- 所有篡改都被服务端纠正或拒绝 → 校验在后端，放弃
- 有签名/加密参数无法复算 → 先解决（见 `sign-param-reverse`）
- 需要真实支付才能验证 → 停，不做

## 六、边界（红线）

| 禁止 | 原因 |
|---|---|
| 完成真实支付/退款 | 涉及资金，越界 |
| 短信轰炸 | 平台明令禁止 |
| 刷券/刷积分获利 | 越界且违法 |
| 并发 >5 或反复压测 | 可能影响业务 |

## 七、常见坑

| 坑 | 说明 |
|---|---|
| 只看前端表现 | 必须看服务端响应与最终状态 |
| 把"能改参数"当漏洞 | 要看服务端是否接受并产生后果 |
| 忽略测试数据清理 | 测试订单/账号要记录，必要时清理 |
| 验证码测太多次 | 容易触发风控，也可能锁定账号 |
