# 后勤维护

> **原则：文件随使用必然增长，这是正常的。不设上限，只做定期减负。**
> 卡上限等于逼自己删掉有用的规则去腾地方——那是本末倒置。

## 一、什么时候启动

**只在用户明确命令时**：说「后勤减负」「后勤体检」「规则库清一下」之类。
平时不要自动跑，也不要因为"感觉有点大"就自己动手。

唯一例外：`verify_change.py budget` 报出**重复长句**或**失效引用**时，可以主动提一句"要不要跑一次后勤减负"。

## 二、体检（只读，不改任何东西）

```bash
PY="<HOME>/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/python/python.exe"

# ① 体积与趋势
"$PY" runs/tools/verify_change.py budget

# ② 各载体的体积
wc -c AGENTS.md OPERATING-MODEL.md runs/notes/派活模板-技能随派.md
for f in ~/.dsh/skills/*.md; do printf "%8d %s\n" $(wc -c <"$f") "$(basename "$f")"; done | sort -rn | head -12

# ③ notes 目录有没有该归档的
ls -1t runs/notes/ | head -20
```

## 三、判定：什么该动、什么不许动

### 永远不许挪出 AGENTS 的（挪了就等于每次都要先想起来加载，那就晚了）

| 节 | 内容 | 为什么 |
|---|---|---|
| §29 | 危害门槛（"我拿到了什么别人拿不到的东西"） | 每次判断都靠它 |
| §31.1 | 所有扫描必须在 Kali | 每次派活都靠它 |
| §11 | 写库必须带 engagement | 每次落库都靠它 |
| §13 | 数据红线 | 每次都靠它 |
| §1–§8 | 基本工作准则 | 每轮都在 |

### 可以挪进技能的

| 判据 | 去哪 |
|---|---|
| 只在**写报告时**用的（结构、截图、措辞、驳回案例） | `butian-submit` / `butian-rejection-cases` |
| 只在**某类漏洞**用的（IDOR/JWT/OAuth/上传…） | 对应能力技能 |
| 只在**结项时**用的（社区学习、HackerOne 校准、反思） | `retro-and-skill-evolution` |
| 只在**踩到某个坑**时用的（软 404、同体、封禁特征） | `field-pitfalls` |

### 该归档进 notes 的

| 类型 | 去哪 |
|---|---|
| 一次性事故的完整经过（时间线、ID、原始报文） | `runs/notes/<主题>-事故.md` |
| 某个工具连挂几次的调试过程 | `runs/notes/改动失效案例.md` |
| 某轮靶标的详细过程 | 靶标自己的 `runs/<靶标>/` |

### 判定问句

> **「如果这条不在 AGENTS 里，我下次会不会犯？」**
> - 会（每次都可能）→ 留
> - 只在特定场景才会 → 挪进技能
> - 只是留个记录 → 归档

## 四、执行（用户确认后才做）

**必须按这个顺序**：

```
1. 备份         cp AGENTS.md runs/backup/AGENTS.md.bak-<日期时间>
2. 改文件       用 edit 逐处替换，不用一次性脚本覆盖（脚本写错目标文件我栽过）
3. L1/L3 验证   grep 确认关键串真的变了、核心判据还在
4. 引用检查     "$PY" runs/tools/verify_change.py budget   ← 看"失效章节引用"必须是 ✅
5. 报告         改了什么、省多少、哪些是挪走（不是删）、备份在哪
```

**绝对不做**：
- ❌ 删掉内容却不留备份
- ❌ 只看脚本打印就报告成功（必须 grep 文件）
- ❌ 挪走 §29/§31.1/§11/§13
- ❌ 为了"看起来清爽"删掉带证据的判据

## 六、和普通"删减"的区别

**后勤做的是「搬迁」，不是「砍掉」**：
- 内容挪进技能 → 需要时 `skill` 加载，信息一点没少
- 内容归档进 notes → 还在，只是不占每轮注入

**只有一种情况是真空删**：内容已经被后续规则推翻（如"旧 §28.1 被 §28.2 覆盖"），且**没有任何地方还需要它**。
这种也要在报告里写明"删的是被谁取代的"。

## 七、这条技能的来历

2026-11-19，我（主会话）试图用「AGENTS.md ≤ 18,000 字符」的硬上限来控制膨胀。
用户否掉了：「文件肯定越来越大，你这样无异于封杀上限」。

**对**——真实需求不是"永远不超过多少"，而是"该轻的时候能轻下来"。
所以改成：**平时不设限，需要时叫后勤来搬一次**。
