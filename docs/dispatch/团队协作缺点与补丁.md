# 团队协作（多智能体）缺点清单与补丁

> 2026-11-14 · 用户要求：把「我因为优点选了这个模式，但暗处缺点会让任务不理想甚至失败」逐条列出来，针对性打补丁。
> 原则：**每条缺点都要能指到本会话/历史真实发生过的现象**，补丁要落在文件、规则或工具上，而不是"注意一点"。

## 零、为什么会这样（根因）

子智能体是**独立上下文 + 独立会话**：它看不到我们之前的调教、看不到其他 agent 的进度、看不到我脑子里的判断。
所以它的输出质量 = **我派活时写进任务的信息量**。派活写漏的东西，不会在它那边自动补上——
它只会用自己的默认习惯填坑，而默认习惯恰恰是没有被调教过的那部分。

---

## A. 信息传递类

### A1 技能/踩坑不随派活传递 ★本会话已发生
- **现象**：我派 `recon-<客户域名>`/`recon-haust` 时只给了动作清单，没点名技能，事后靠 `send_message` 补发。
- **根因**：以为角色提示词里的"技能路由"够用，实际它只是一句指引，不含参数与判据。
- **后果**：子智能体凭记忆写 nmap/httpx/crt.sh 参数，漏掉 UA 隐身、泛解析否证、限速这些已踩过的坑。
- **补丁**：AGENTS.md §16 + `runs/notes/派活模板-技能随派.md`；回报必须含「实际加载/增用/为什么」。

### A2 情报在转述中失真
- **现象**：预解析表、已知 IP 组、排除项，全靠我在任务描述里复述；我漏一行，它就少一个资产。
- **补丁**：**关键情报落盘**（`runs/<靶标>/pipeline-state.md` + `runs/notes/六靶标主机名变体预解析.md`），
  派活时写"先读这两个文件"，而不是让我口述。

### A3 子智能体上下文被扫描输出撑爆
- **现象**：nuclei/目录爆破原文几千行塞进上下文 → 后半程丢指令、重复跑、忘记落库。
- **补丁**：任务里写死——**原始输出一律落盘**（`runs/<靶标>/recon/*.txt`），只把结论/计数带回报；
  单资产给时间盒（如 45 min），到点先回报再决定续不续。

## B. 数据一致性类

### B1 写库不传 engagement → 串进别家库 ★历史 2 起事故
- **补丁**：AGENTS.md §11 + 每个子任务第一段写 `engagement="<单位名>"` 并允许它 `redteam_session_bind` 兜底；
  **回报必须给 asset_id/vuln_id**；我用 `dbcheck.py` 抽查。

### B2 会话绑定继承错（本会话真实风险）
- **现象**：我绑的是华东交大，同时派河南科大的 agent —— 它默认继承我的绑定，`redteam_asset_query` 会读到华东交大的库。
- **补丁**：跨靶标派活时，任务第一行写「开工先 `redteam_session_bind engagement="<你的靶标>"`」；
  回报里要数字（资产/漏洞条数），我用 `dbcheck.py` 比对该库是否真有增量。

### B3 回报注水："说做了、库里没有" ★多智能体头号坑
- **补丁**：**看不到 = 没发生**。新增 `runs/tools/dbcheck.py`（只读 SQLite）：
  ```
  PY=<HOME>/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/python/python.exe
  "$PY" runs/tools/dbcheck.py --all
  ```
  输出每个靶标的资产/端口/指纹/漏洞分状态/HTTP 证据/截图/凭据/隧道/得分/清理遗留 + 告警。
  已实测：华东交大 16 资产(13 live)/27 端口/35 指纹/0 漏洞/全部 untested → 告警"只落了资产没测"。

### B4 多 agent 重复打同一资产
- **补丁**：派活前查 `redteam_asset_query` 的 `test_status`；**一个资产同一时间只归一个角色**；
  每测完立刻 `redteam_asset_test` 回写（status/test/surface），否则后面一定重复打。

## C. 资源与噪声类

### C1 Kali 2 任务上限被多 agent 争抢
- **现象**：每个 agent 各自 `nohup` 起扫描，两个 agent 就是 2 个任务，再加一个就拖垮 8 vCPU。
- **补丁**：`redteam_agent_slot` 闸门 + 每个子任务写死「**你同一时刻最多占 1 个 Kali 任务**」；
  收口时必须 `pkill` 遗留后台任务并在回报里说明。

### C2 噪声叠加
- **现象**：我允许每个 agent 5 req/s，两个 agent = 10 req/s，直接踩"1 秒 10 条换整站封 IP"的坑。
- **补丁**：**噪声预算按总量分配**——写进任务："本靶标总预算 ≤5 req/s，你一个人用不超过 3 req/s"；
  敏感路径（登录、导出、备份）一律逐条 + 间隔 ≥1s。

### C3 封禁联坐
- **现象**：一个 agent 把出口 IP 打封，另一个 agent 在同一出口下也全废，但它以为是"目标挂了"。
- **补丁**：任务里要求"被封立刻停并如实记阻塞，**不换出口、不用代理池**"；
  我在派下一个 agent 前先看 `redteam_asset_query` 的 `blocked_count`。

## D. 判断质量类

### D1 共模错误（同一个模型犯同一个错）
- **现象**：两个 agent 都漏 UA、都用同样的错误参数、都把 WAF 的 404 当真基线。
- **补丁**：技能点名（A1）+ **复核必须换方法**：换命令（curl ↔ Burp）、换工具（nuclei ↔ 手工）、
  换证据类型（回显 ↔ 截图 ↔ 库记录）。**不接受"另一个 agent 也这么说"当复核**。

### D2 假阳性互相印证
- **补丁**：每条 vuln 必须有 `evidence` 里的**可重放原始请求**；无请求 = candidate，不升级 confirmed。

### D3 范围漂移（自行扩到 T2 旁站/C 段）
- **补丁**：任务里写死 T 级门槛（T0/T1 可打，T2 必须先回报我，T3 停）；
  回报单列「**新增资产及其归属证据**」，我逐条核；`dbcheck` 看资产数量异常增长。

### D4 指令冲突（角色提示词 vs 我的任务描述）
- **补丁**：任务里写一行优先级：**授权与红线 > 我的任务描述 > 角色提示词默认路径**。
  角色说"只收集不验证"，我的任务若让它顺手验一条，必须显式写"例外：这一条可以验，因为…"。

## E. 流程收口类

### E1 遗留物无人管（马/隧道/账号/文件）
- **补丁**：建了就 `redteam_cleanup op=add`；`dbcheck` 会报 `清理 open`；
  隧道 active 未关会告警；交付前必须清零或写"kept + 理由"。

### E2 台账/收口漏做
- **补丁**：收口四件事（AGENTS §14）逐条写进每个子任务末尾，不靠自觉；
  `dbcheck` + `update_status.py --list` 双向核对。

### E3 成本失控（并行 + goalRun 多轮 + 忘关 cron）
- **现象**：历史上有靶标跑完 cron 没关，次日自动重跑白烧额度。
- **补丁**：目标达成即关 `task_board_schedule`；goalRun 的卡只在大活上开；
  停止条件（≥3 条可提交 / 连续 2 阶段无新增 / 触红线）写进任务，避免无限续跑。

---

## F. 我（指派者）自己的瓶颈

### F1 我串行派活 = 我成为瓶颈
- **补丁**：只有**互不依赖**才并行，上限由 `redteam_agent_slot` 决定；
  我这边只做"读库—核对—派活—汇报"，不下场动手（避免上下文被扫描输出吃掉）。

### F2 我读回报会漏项
- **补丁**：固定核对五问（下表），不靠"读着觉得对"。

### F3 并发数据不可观测
- **现象**：本会话 `redteam_agent_slot status` 返回 `registry_available: false`（注册表不可用），
  跑数只能靠预留计数。
- **补丁**：以 `list_agents` 为准；派活前后各看一次；出现"说在跑但没产出"就 `send_message` 要进度。

## 派活前 30 秒清单（每单必过）

1. `redteam_agent_slot status` —— 还有名额吗？Kali 还剩几个任务？
2. `redteam_asset_query` —— 这个资产/靶标是不是已经在打？（看 test_status、blocked_count）
3. 任务描述五段齐了吗：**范围+排除 / 已知情报+已测过什么 / 指定技能 / 动作+落库 / 回报结构**
4. 红线三行齐了吗：**engagement 显式 / 噪声与 Kali 任务额度 / T 级门槛与停止条件**
5. 这个活的产出我能用什么核对？（asset_id / vuln_id / 截图 / `dbcheck.py`）

## 回报核对五问（每单必问）

1. 库里有没有对应记录？（`dbcheck.py` / `redteam_asset_query` / `redteam_vuln_query`）
2. 数字对不对得上？（它说的资产数 vs 库里的增量）
3. 高价值成果是不是换了方法复核？（同一模型重复结论不算）
4. 范围有没有越界？（新增资产能否给出归属证据）
5. 遗留物清理了吗？（cleanup / 隧道 / 后台任务）
