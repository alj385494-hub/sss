# 社区思维切入点库

> 来源规则：AGENTS §25 —— 摘"作者为什么怀疑那里"，不只摘 payload。
> 每条格式：**直觉原话 → 背后假设 → 在我的靶标上怎么验 → 验证办法**。

## I1 · "没有过滤、直接传递，怎么可能没洞"（2026-11-14）

- **来源**：[《浅析JAVA代码审计中的"幽灵代码"》](https://forum.butian.net/share/1118)（2021-11-19，奇安信攻防社区，Alivin）
- **直觉原话**：「在很多看起来没有做任何过滤处理、没有任何权限设置的漏洞链中，却无法完整复现漏洞。
  讲道理这里没有任何过滤，直接传入到 xxx 里面，怎么可能会没有 xx 漏洞呢？」
- **背后假设**：**校验不在你看的那一层**。Java 系统的鉴权/过滤常发生在 **Filter / Interceptor / Spring AOP**
  这些"切面"里，控制器代码看起来"裸奔"，实则被外层统一拦掉；反之，外层漏配时控制器就直接暴露。
- **在我靶标上怎么验**：
  1. 把"控制器前的那一层"当成独立攻击面：查 `web.xml` 的 filter 顺序、Spring Security 配置、`HandlerInterceptor`；
  2. 若外层是**网关/中间件**（aTrust、nginx、Express），要验证鉴权是"**路由分发前**"还是"分发后"——
     这决定"接口清单里找漏鉴权"是否还有意义；
  3. 反向利用：外层按 **HTTP 方法/路径规范化**判定时，找**方法维度遗漏**（本靶标实测 OPTIONS 跳过零信任校验）
     与**路径规范化差异**。
- **验证办法（已落地成判据）**：
  - 先测**不存在的方法/裸前缀**拿拒绝基线；若与真实接口**同体同长同状态码** → 鉴权在路由前 →
    停止逐接口枚举，转"拿 token / 绕网关"（已写进 `api-noauth-hunt` 阶段 2 第 0 步）；
  - 对照同一网关上的**被拦 vhost 与放行 vhost**（本靶标实测 yjsxt 豁免、oas 被拦）。
- **本靶标实证**：某网络设备厂商开放平台 16 个接口 + 裸前缀全部同一个 51B 401（鉴权在路由前）；
  华东交大 aTrust 网关上 OPTIONS 方法跳过 verify（方法维度漏配）。

## I2 · "一处有鉴权"不等于"整站没越权"（2026-11-14）

- **来源**：[《SRC 视角下：渗透测试中的逻辑漏洞思路博弈》](https://forum.butian.net/share/4441)
- **直觉原话**：「大多数人在一个站比如测试越权发现有鉴权，就下定义觉得这个站已经没有越权了，这是万万不行的，
  作为白帽子最后是把所有思路穷尽才算是一次完整的渗透测试。」
- **背后假设**：鉴权实现**按功能点逐个写**，必然参差；一个接口拦得住，另一个接口可能忘了。
- **在我靶标上怎么验**：拿到"接口清单"后，**按功能点分类穷举**（查询/导出/详情/审批/下载），每类至少各试一次
  "删除或替换鉴权参数"；判据是"同一批接口里是否存在 1 个响应体结构不同"。
- **验证办法**：`api-noauth-hunt` D1–D5 五档**按功能点分组**执行，而不是只挑最像的那个接口；
  一旦某个接口 401，不要就此判定整站安全，继续把同类接口跑完。

## I3 · 按"漏洞出现的位置"穷举，而不是按扫描器（2026-11-14）

- **来源**：[《谈谈业务逻辑漏洞》](https://forum.butian.net/share/1453)
- **直觉原话**：「逻辑漏洞大概出现在如下几处……支付处存在的逻辑漏洞很多，但是一言以蔽之：**数据篡改**。」
- **背后假设**：业务漏洞有**固定发生位置**（登录/注册/支付/查询/审批/导出/绑定），
  每个位置有固定的"可变数据"（数量、金额、身份、状态、时间）。
- **在我靶标上怎么验**：把资产按"业务位置"打标签，逐个位置问：这里的哪些字段**改变后不该被接受**？
  （缴费系统=金额/订单状态；教务=学号/学期；一卡通=卡号/余额）
- **验证办法**：只做**只读观察 + 不合法值试探**（如不存在订单号），**绝不下单/不支付/不改真实数据**。

## I4 · 先看请求里"少了什么"：无 sign 校验 ⇒ 优先怀疑可篡改（2026-11-14）

- **来源**：[《小程序渗透记录：通过细节挖掘漏洞的艺术》](https://forum.butian.net/share/4229)
- **直觉原话**：「创建订单观察到**并没有 sign 校验字段**，存在问题可能性较大。而后开始对每个存在字段的数字
  增增改改，观察到底是哪个字段可以影响订单的生成。」
- **背后假设**：**缺签名 = 服务端信任客户端提交的字段**；有签名时反而要先逆向算法。
- **在我靶标上怎么验**：抓包后先做"字段清单减法"：没有 sig/sign/timestamp/nonce → 直接进"字段篡改"路线；
  有签名 → 先看签名覆盖范围（是否漏签某个参数，改漏签的那个往往不校验）。
- **验证办法**：逐个字段改值看**响应差异**（价格/状态/归属变化）；只改到"服务端接受但业务结果异常"即停。

## I5 · 输出点 → 输入点：把响应里的字段拿去打别的接口（2026-11-14）

- **来源**：[同上 4229](https://forum.butian.net/share/4229)，作者引用 L@2uR1te《如何寻找参数的蛛丝马迹》
- **直觉原话**：「**输出的参数拿到输入点去使用会有不一样的惊喜**……只要一个点可以越权查看到别人的某些东西，
  把他人信息的敏感参数收集下来替换到其他输出点使用，尝试是否能看到对应的信息。」
- **背后假设**：**鉴权字段/身份标识在不同接口间不统一**（有的走 Cookie、有的走 query 的 uid、有的走 body 的 openId）。
- **在我靶标上怎么验**：任一响应体里出现 `userId/openId/orgId/cardNo/phone/token/accessToken` 这类字段，
  立刻登记为"**可用输入素材**"，逐个塞到别的接口的参数里试；重点看"同一用户体系里的不同接口"。
- **验证办法**：**双账号对照**（有账号时）或"用自己的标识 vs 换成他人标识"看响应体差异；只读，不改数据。

## I6 · 前端脱敏 ≠ 后端脱敏（2026-11-14）

- **来源**：[同上 4229](https://forum.butian.net/share/4229)
- **直觉原话**：「手机号是脱敏的手机号，提上去肯定是危害没那么大的，**不过一般都是前端脱敏的，可以强开 F12 看看源代码**。」
- **背后假设**：展示层的 `138****1234` 经常是**接口返回全量、前端打码**；接口原始响应仍含明文。
- **在我靶标上怎么验**：任何"页面显示脱敏"的地方，直接看 **F12 → Network 的原始响应**（不是页面文字）；
  若响应里是明文 → 属信息泄露（补天口径：能拿大量敏感信息=高危）。
- **验证办法**：只取 1–3 条样本 + 接口自报条数，`redteam_data_proof` 落库；**不批量导出**。

## I7 · 票据/令牌跨服务复用：只校验"有效"，不校验"受众"（2026-11-14）

- **来源**：[《微服务下统一认证风险总结》](https://forum.butian.net/share/898)（该文需登录，本次仅读到摘要，**待补读全文**）
- **直觉原话（摘要级）**：统一认证把凭证下发给多服务后，"为每一个服务写一套认证服务会浪费很多人力"，
  于是各服务共用同一票据体系 → 带来新的风险。
- **背后假设**：票据（CAS ticket / JWT / SSO session）在服务端只校验**是否有效**，不校验**是不是发给这个服务的**。
- **在我靶标上怎么验**：拿到任意一个服务的票据后，去**另一个服务**的同族接口重放（换 Host、换 service 参数），
  看是否被接受；CAS 场景注意 `service` 白名单与 ticket 一次性。
- **验证办法**：先在中性服务上试（不要动生产审批流），只读接口优先；记录"接受/拒绝"差异作为证据。
