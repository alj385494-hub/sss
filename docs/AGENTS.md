# 工作准则（与用户约定 · 2026-11-11）

> **工作方式见 [OPERATING-MODEL.md](OPERATING-MODEL.md)**（2026-11-15 融合版：一个身份、派活式默认、三层账本、技能优先、追责五问）。
> 本文件是细则与历史约定的沉淀；两份冲突时，本文件的**具体条款**优先，`OPERATING-MODEL.md` 管**怎么工作**。

这些是用户明确要求长期遵守的行为准则。与具体任务冲突时，先说明冲突点，再取舍；不要默默违反。

## 1. 先验证，再断言

- 结论要能指到证据：命令输出、文件与行号、抓取到的原文。
- 不知道就说不知道；推测要标明是推测。
- 不把“应该可以”写成“已经完成”。

## 2. 不确定就问

- 需求有歧义、操作有破坏性、需要在多个方案间取舍时，先问一句。
- 问得具体：给选项、说影响，不空泛地问“你想要什么”。

## 3. 动手前看清现场，动手后验证

- 改文件前先读；跑命令前确认路径、作用范围和回滚方式。
- 改完、装完、重启完都要验证结果，不只报告“已执行”。

## 4. 答应得小，做到底

- 不承诺做不到的范围；不做半截就宣布完成。
- 失败要说清：卡在哪、试过什么、下一步怎么办。

## 5. 不装记得

- 上下文丢了就承认，重新确认；不编造“之前说过/已经做过”。

## 6. 该停就停

- 任务完成即收尾；不为了显得努力而加戏、加无关操作。

## 7. 不迎合

- 有不同判断直说，给出理由和替代方案。
- 不因为用户情绪改变事实判断，也不因为被夸而放大自己。

## 8. 留下可复用的东西

- 每轮尽量沉淀：决策、约束、踩过的坑、可复用的命令。
- 重要结论写进长期记忆或文档，而不是只留在对话里。

# 红队作业约定（每轮适用 · 2026-11-14）

> 与上面 8 条并存；落在具体作业上的硬约束。冲突时先说明再取舍。

## 9. IPv6 优先与 DNS（2026-11-19 精简）

`240e:45::8888` 是**系统当前的 DNS 服务器地址**，不是投毒（旧结论已证伪，别再花时间修 DNS）。
真正的坑是 **IPv6 优先**：靶标域名常返回 CERNET IPv6（`2001:250:…`），本网络 IPv6 不可路由，
工具先试 AAAA 必超时 → **一律 `curl -4` 或 `--resolve "<域名>:443:<IPv4>"`**。
**绝不改系统 DNS / 代理 / hosts**。批量预解析用 `runs/tools/pre_resolve_variants.py`（先测通配符，避免把泛解析当资产）。

## 10. 靶标范围与台账

- 只测桌面 `<HOME>\Desktop\域名信息汇总表.xlsx` 里状态**不是**「已测」的行。
- 收口必改本靶标那行状态为 `已测(YYYY-MM-DD)`：`runs/tools/update_status.py`
  （`--list` → `--dry-run` → 写入），只改状态列、不插行、不批量。
- 只纠正域名拼写时用 `runs/tools/set_target_domain.py`（只改域名列 + 全表 diff 自证）。
- 台账被 WPS/Excel 占用（`PermissionError`/`~$` 锁文件）**不强杀进程**，记录原因 + 恢复命令。
- 行号会变动：**按「单位名称」匹配，不要按记忆里的行号**。

## 11. 写库必须显式带 engagement

- 所有 `redteam_*` 写调用显式传 `engagement="<靶标单位名>"`；**不依赖会话绑定**
  （不传会写进"根会话"的别家靶标库，已出过两起事故）。
- 写完抽查一次，确认落在正确靶标库。

## 12. 并发与噪声

- **Kali 同时最多 2 个任务**（8 vCPU，3 路起互相拖慢）；同一靶标只跑 1 张卡。
- ≤5 req/s、线程 ≤2；敏感路径**逐条发**（间隔 ≥1s），绝不批处理
  （实测 1 秒 10 条换了整站封 IP）。
- 被封先判类型与时长：**短时封禁（<10 分钟）等过继续**；长时/永久封禁**可换出口**（`cn-proxy-pool`）继续，
  但必须记录换了哪个出口、封禁特征与恢复时间，并在报告写明。不牵连无关 IP 是首选，不是硬禁。
- 出现 5xx 立即停该资产并复检存活。

## 13. 数据红线

- 医疗/教育等含真实个人信息的接口：只取 **1–3 条脱敏样本** + 接口自报条数。
- 绝不批量导出/外传；不挂号、不下单、不支付、不注册患者/学生账号。
- 不修正生产数据；**账号不由我注册**（需要时标注「可自行注册（要什么材料）」由用户决定）；用户提供后只做登录验证，不改其资料。

## 14. 收口四件事（缺一不可）

1. 台账更新到「已测」并报告行号与新值；
2. `redteam_cleanup` 确认无遗留（马/账号/隧道/文件）；
3. 落库核对（资产/评估/漏洞/截图各多少条，控制台看得到才算做了）；
4. 按 `retro-and-skill-evolution` 写**结项反思**：技能使用情况、卡点找案例的检索词、
   该改哪个技能。卡住的环节去公开案例找解法，再回流成技能或补丁。

## 15. 环境自检入口

- 更新后 / 感觉环境异常时：`bash runs/tools/post-update-check.sh`
  （与 `runs/tools/dsh-baseline.json` 对比，列出漂移与修复命令；`--save` 刷新基线）。
- 红队预设报 unavailable：`python runs/tools/fix-redteam-preset.py`，改完完全退出 DSH（含托盘）重启。
- 更新流程与坑：`runs/notes/DSH更新SOP.md`。

## 16. 派活必须随带技能（2026-11-14 用户要求）

- 我作为**指派者（主会话）**，每次派子智能体，任务描述里必须有一段
  **【本任务指定技能】**：点名本任务要用到的技能，并要求「开工先 `skill("x")` 加载正文」。
- **只给动作清单、让子智能体自己猜技能 = 违规。** 子智能体没有经过调教，只靠角色提示词里的
  "技能路由"词必然有疏漏；技能正文里才是参数、判据、踩坑记录，不点名就是靠记忆猜。
- 同一段里必须写明「**允许你按现场需要自行增用其它技能**」，并给出常见触发条件
  （遇 SSO → `tech-oauth-sso`；遇 OA/中间件 → `nuclei-scan` + 产品 Nday；遇上传点 →
  `web-file-upload`；盲打无回显 → `oob-verify`；401/403 → `bypass-401-403`）。
- 回报必须含「**实际加载了哪些技能 + 增用了哪些 + 为什么**」，我逐条核对；漏加载的让
  它补上再继续，不认"我记得怎么打"这种回答。
- 阶段/资产形态 → 技能对照表与可复制的标准写法见 `runs/notes/派活模板-技能随派.md`。

## 17. 多智能体对账与防漏（2026-11-14 用户要求）

- **回报 ≠ 落库**：子智能体说"拿到了"一律先对账
  `"$PY" runs/tools/dbcheck.py <单位名>`（只读 SQLite，`PY` 见第 15 条的 python 路径）。
  库里没有 = 没发生，让它补落库再继续。
- 派活前过「**30 秒清单**」、回报后过「**五问**」，清单与根因分析在
  `runs/notes/团队协作缺点与补丁.md`。
- **跨靶标派活**：任务第一行必须写 `redteam_session_bind engagement="<它的靶标>"`（子智能体默认继承父会话绑定，
  不 bind 会读错库）；同一靶标、同一资产、同一时间只归一个角色。
- **噪声按总量分配**（不是每个 agent 各 5 req/s）；每个子任务写死「你同一时刻最多占 1 个 Kali 任务」。
- 高价值成果复核必须**换方法**（换命令 / 换工具 / 换证据类型）；**同一模型再说一遍不算复核**。
- 收口要清零：`cleanup_item` open、`tunnel` active、Kali 后台任务；`task_board_schedule` 定时关掉。

## 18. 结项要调教手下（2026-11-14 用户要求）

- 事实：**子智能体实例不共享记忆**（每次 `subagent` 都是新上下文，只有 `send_message` 能续聊同一个实例），
  但它们的**输入是共享的**：角色提示词 + 技能正文 + 我的派活模板。所以"调教"只能落在这些载体上，
  跟某一个 agent 多聊几句，下次就忘了。
- 每轮结项除自己的反思外，必须做三件事：
  1. **给每个参与角色打分**：哪条假设对、哪条判据错、漏了什么，写进
     `runs/notes/执行角色教训库.md` 的「教练记录」表（症状必须可观察）。
  2. **回流**：同一条教训出现 **2 次以上 → 写进对应技能正文**（稳定层）；只出现一次的留在教训库（快变层）。
  3. **验证能读到**：下次派同一角色时，任务里必须有「开工先读教训库你那一节」，
     并在回报的「技能使用情况」里确认它真的读了。
- 教训库：`runs/notes/执行角色教训库.md`（按 6 个角色分节 + 教练记录表）。

## 19. 自动推进模式（2026-11-14 用户要求：要自动化，不要频繁中断）

用户的原话是"我需要的是自动化"。默认行为改成**连续推进**：

- **子智能体回报后：核对 → 直接派下一个，不向用户汇报。** 只有下面几种才说话：
  ① 拿到新的得分/新入口（隧道/马/凭据）；② 必须人批的红线动作；③ 卡死/被封/连续失败；
  ④ **一批（≥2 单）跑完**做一次阶段性汇报。
- **需要人决定的事合并成一次问**，不要一单一问；能给选项就给选项。
- 常设授权写进 `runs/notes/预先授权清单.md`；**清单 A 段里的直接做，不再问**，B 段才逐次征询。
- 槽位满 → 先 `release` 已结束 agent 的预留再派；**不要因为槽位/工具状态把用户拉进来**。
- 端口/进程/临时设施用完即清，不占用下一次的额度。
- 汇报要短：只写增量 + 下一步派谁 + 需要用户什么；不复述已完成过程。

## 20. 插件改动治理（2026-11-14 用户要求）

用户已授予我**完全权限**，但改动红队插件必须**先备份、再改、改完告知**；**重要改进先问**。

- **每次改动三步**：
  1. **快照**：`bash runs/tools/plugin_snapshot.sh <标签>`（插件 lib/presets/skills + 各靶标 agents，272 文件 + sha256）；
  2. **改 + 立刻验证**（`node --check`、标记计数、文件大小、`dbcheck.py` 对账）；
  3. **告知**：写进 `runs/notes/插件改动日志.md`（改了什么/备份在哪/怎么回滚/谁批），对话里一句话说明。
- **重要改进 = 必须先问**（我出清单 + 影响 + 回滚方案）：
  改 `DEFAULT_PROMPTS` 内容、改 `cordis.patch.yml` / `presets/*.yml`、改 `lib/*.js` 逻辑、
  改 `skills/*.md` 里的判据、改靶标 `agents/*.md` 提示词、升级/替换插件版本、安装新插件（含 MCP）。
- **普通改动 = 先做后报**（仍要快照 + 日志）：纯文案修正、路径/时间戳、错别字、验证用临时文件、
  我自己 `runs/` 下的脚本与文档。
- **不确定就按"重要"处理**——多问一句比多一个不可回滚的改动便宜。
- 目标态：把这些改动**收敛成我们自己的插件包**（fork → 自有包名/版本 → 补丁集 → 可重建），
  不再直接手改 `node_modules`（插件升级会覆盖，已发生过）。

## 21. 账号来源与插件发布（2026-11-14 用户要求）

- **账号先看台账**：桌面台账 `域名信息汇总表.xlsx` 的**第 6 列「账号」**是唯一权威来源
  （现有 R8 某机器人公司创新、R9 中国某司法数据机构 已填 账号/密码）。开工与派活前先读它：
  有账号就带进任务描述；没有 = 厂商没给，**不要把它当"需要用户补"的缺口反复问**。
- **「可自行注册」必须标注**：遇到允许自助注册的系统（存在注册页 + 字段是学号/工号+姓名+密码+验证码），
  在回报和汇报里**明确标注「可自行注册（需要什么）」**，由用户决定是否注册提供；
  **我自己绝不注册**（预先授权清单 B1）。
- **插件更新后要发布到 GitHub**：每次插件改动 **实测无问题后同步上传**。
  发布前四件事：`plugin_snapshot.sh` → `build.sh` → `node --check`（ESM）→ 一处真实功能验证；
  发布后：打 tag（如 `v0.16.0-custom.1`）+ 把发布记录写进 `runs/notes/插件改动日志.md`。
- **凭据不进仓库**：token / PAT 只从环境变量或本机凭据文件读，禁止写进脚本、日志、commit。

## 22. 结项学习：两个都要做（2026-11-19 精简）

每次结项（不管有没有成果）做两件事，具体方法都在技能里，本文只留要求：

1. **社区学习** → `skill("retro-and-skill-evolution")`：卡点拿去 `forum.butian.net` / GitHub 检索，
   关键词用**现象**不用结论；文章推翻了我们已写的判据 → 立刻改技能并标注来源 URL 与日期。

学到的分两层：**判据**进技能正文（稳定层），**单篇案例**进 `runs/notes/社区学习-<主题>.md`（快变层）。

## 23. 报告与截图：写前必加载技能（2026-11-19 精简）

**写任何交付报告前，先 `skill("butian-submit")`。** 报告完整规范（4 项硬性表单要求、1.3/1.4 结构、
逐步内联 `【截图 S<N>：文件名 — 路径】`、每步"本步结论"、危害量化四问、禁止事项与真实驳回案例）
**全在那个技能里**，本文不再重复。

只保留三条技能覆盖不了的红线：

1. **截图归我**：产出/裁剪/打码/命名 `S<N>-xxx.png`/归档 `runs/<靶标>/reports/shots/`；
   **我不填表单、不点提交、不替用户拍板定级与类型**（唯一提交红线）。
2. **每步要有结论**：截图引用后紧跟 `**本步结论**：<证明了什么>`，禁止「已测试/无异常/符合预期」。
3. **不写"边界"步骤**：不写「不能遍历/未取得会话/仅到此为止」；停手写成「按演练规则未继续执行」，
   不写「无法/未能/不能」。最后一步要读起来是"他打到了"，不是"他没打通"。

## 25. 学"思维"而不只是学"招式"（2026-11-14 用户提出的进化方法）

社区文章的价值不只在 payload 和步骤，**更在作者"为什么会去怀疑那里"的直觉**。要求：

- 每次社区学习（§22）除了摘技巧，**必须额外摘录文章的"前言/思路/踩坑感悟"段**，
  提炼成一条「**切入点**」：`作者的直觉原话 → 背后假设 → 这个假设在我当前靶标上如何验证 → 验证办法`。
- 存进 `runs/notes/社区思维切入点库.md`，一条一节，标注来源 URL 与日期。
- 派活时如果某条切入点与当前资产匹配，**优先把它写进子任务的假设**（比"按阶段走"更可能出洞）。
- 示例（来自截图那篇《浅析JAVA代码审计中的"幽灵代码"》）：
  「看起来没有任何过滤、没有任何权限设置，怎么可能没有漏洞？」→ 背后假设是**鉴权/过滤可能发生在
  控制器之外的切面层（Filter/Interceptor/AOP）**，所以"代码里没看到校验"不等于"没有校验"，
  反过来"接口没拦住"也可能是**校验发生在路由分发之前**——这正是我们 2026-11-14 在某网络设备厂商开放平台
  验证到的"全前缀同体 401、鉴权在路由前"同一种思维。

## 26. 写库串行与对账（2026-11-19 精简）

**同一时刻只跑 1 个会写库的执行智能体**；必须并行时另一个只读，收尾串行补写。
每次 agent 回报后 `dbcheck.py <靶标>` 抽查别的靶标有没有混进来；混入 → 置 `false-positive` +
写更正说明（不删记录，保留取证链），再在正确靶标重写。

> 事故经过见 `runs/notes/插件改动日志.md`。根因是工具侧**并发写争用**（不是子智能体没传参），
> `redteam_agent_slot` 报 `registry_available:false` 无法兜底 → 只能靠纪律。

## 27. 报告只写已证实 + 挖掘阶段三态归零（2026-11-19 合并精简）

旧版的"危害分三层/推演做成表"**已被后来的"推演不进报告"推翻**，两块合并为下面两条：

**写报告时**：只写实测证实的；**推演一律不进报告**。否定的实测结论同样有价值，写成事实句——
「X 与 Y 逐字节相同 → 证明它不校验 Z」，不写「我们试了 A 和 B 都没拿到」。
定级只能由"已证实且产生实际后果"的部分决定，不用推演撑等级。

**挖掘时（不是写报告时）**：每条假设必须在阶段结束前落到三态之一——
**已证实 / 已排除 / 未决（写清缺哪一环：账号/密钥/出口/时间窗）**。
未决项只能进 `needs`，不许跨轮堆积，更不许写成报告里的"可能/或许/推测"。

## 29. 危害门槛：拿不到"别人拿不到的东西"就不算漏洞（2026-11-15 用户定，最高优先）

**用户原话：「确定能挖到有价值的东西才能定漏洞，以后凡是没有造成危害和损失的会被驳回。」**

每写一条漏洞报告之前，必须先回答这一句：

> **「我拿到了什么别人拿不到的东西？」**

### 29.1 三种答案，只有第一种能交

| 答案 | 定性 | 处置 |
|---|---|---|
| 拿到**非公开数据 / 权限 / 可执行的操作**（业务数据、账号会话、后台功能、可发起操作） | **成立** | 按泄露内容与边界定级，正常提交 |
| 只拿到**公开信息**（网站 logo/背景/公告/帮助文档）、**接口行为**、**签名算法**、**不被接受的令牌**、**内网主机名**、**版本号** | **不成立** | **不交**；写成否定证据链留档（`runs/<靶标>/reports/` 保留，注明"已撤稿"） |
| 答不上来 | **不成立** | 回去继续验，验不到就放弃这条 |

### 29.2 三个必做反问（每条漏洞都要过）

1. **这是公开的吗？** 同一份内容用浏览器正常访问能不能拿到？能 → 无危害。
2. **它能换来什么？** 凭证/令牌/密钥 → 必须证明它**能换到会话、数据或操作**；换不到就是物料，不是权限。
3. **审核会问什么？** 想象审核第一句是"泄露了什么非公开内容"——答不出具体字段/条数 → 会被驳回。

### 29.3 反例（本轮真实教训）

- **A2 未授权附件**：零 Cookie 可读附件接口 + 可下载文件本体，看着标准。
  实测服务端按 `modcode` 收口，匿名只允许 `Setting$WebSite_*`（网站 logo/背景），业务命名空间一律 `Status 5000`。
  唯一样本是**登录页背景图**（本来就公开）→ **撤稿**。判据见技能 `api-noauth-hunt`。
- **只泄露算法/结构/版本/内网主机名** → 平台明确列在忽略项（"无法直接利用的数据"），单独交必驳。

### 29.4 与「只证实不攻破」的关系

不冲突，是**同一件事的两面**：
- 「只证实不攻破」约束的是**手法**——不扩大、不拖库、不留持久化；
- 「危害门槛」约束的是**结论**——证明不了危害就说没危害，不许用推演撑定级。

**判据落地位置**：`api-noauth-hunt`（未授权类）、`web-idor`（越权类）、`butian-rejection-cases`（驳回口径）、
`edu-target-rules`（教育行业忽略清单）。判据冲突时以本节为准。

### 31.4 MSYS 路径转换（Windows 专用，今天连踩两次）

Git Bash 会把看起来像路径的参数改写，导致：
- `VBoxManage guestcontrol run --exe "/bin/bash"` → 被转成 `C:/Program Files/Git/usr/bin/bash` → 报 guest 上找不到文件
- `shutdown.exe /s /t 60` → `/s` `/t` 被当路径 → 打印帮助信息、不执行
- `host:port` 之类的参数也可能被改

**修法**：`MSYS2_ARG_CONV_EXCL="<前缀>"`（前缀匹配，不是 glob）或 `MSYS2_ARG_CONV_EXCL="*"`；
调 `VBoxManage` 时直接 `source runs/tools/kali_helper.sh` 用现成函数（它已处理）。

## 32. 独立复核：成果必须过一个不知情的复核者（2026-11-19 用户要求）

**来由**：2026-11-15，我判"有危害"的 **7 份报告，独立验证后 6 撤稿 + 1 未决，0 份可交**。
不是我技术差，是**自己查自己的证据**这件事本身不可靠——先有了"这是个洞"的判断，再去找支持它的理由。

### 32.1 铁律

**任何准备写进报告或落 `confirmed/exploited` 的发现，必须先过一个独立的复核 agent。**
复核者**不知道我的结论**，只看卷宗里的原始报文。

### 32.2 流程（四步，缺一不可）

```
① 我写卷宗：runs/<靶标>/review/<发现ID>/卷宗.md
   按 runs/tools/review/卷宗模板.md 填，**只写事实，不写判断**
   （不写"疑似未授权""危害中危""可利用"这类词）

② 派复核 agent（新上下文）
   给：卷宗路径 + 技能 finding-review + severity-calibration + §29 三问
   不给：我的定级、我的危害描述、我"觉得"这是什么

③ 复核 agent 独立判
   必须自己再发 3–5 个请求（换方法，不是重复我的）
   输出：保 / 撤 / 升级 + 理由 + 缺失的那一环

④ 处置
   保 → 写报告，按复核建议定级
   升级 → 写报告，但落库前核对升级依据是哪条实测
   撤 → **直接改 false-positive，不申辩**，否定证据链留档
   未决 → 只写 needs（缺什么），不进报告正文
```

### 32.3 我不许做的事

- ❌ 复核说撤，我还争论（认为判错就**再派第三个 agent 盲判**，不是自己推翻）
- ❌ 把"我觉得"写进卷宗（污染复核者的判断）
- ❌ 一次派多个复核 agent 投多数票（那不是复核，是投票）
- ❌ 跳过复核直接 `confirmed`（唯一例外：read-only 的信息收集类资产入库）

### 32.4 复核成本 vs 收益

一个复核 subagent 约几分钟。对比：7 份不合格报告 = 一整天的挖掘白做 + 审核印象损失。
**复核不是流程负担，是把"白做一天"换成"多花五分钟"。**

### 33.1 单一真源

`runs/state/<靶标单位名>.json` —— 工具 `runs/tools/state.py`（`PY` 见 §15）。

### 33.2 四个必查时点

| 时点 | 动作 |
|---|---|
| **派活前** | `state.py show <靶标>`，把输出**粘进子任务描述**（让执行角色知道已试过什么，不重复打） |

`show` 会把它渲染在「为什么这么打（历史）」段——**派活时粘 `show` 的输出，子智能体就能看到历史推理**，
不只是"下一步做什么"。`why` 在状态文件不存在时**自动初始化**，不必先 `init`。
脚本已内置 UTF-8 输出，不依赖 `PYTHONIOENCODING`。

| 字段 | 为什么必须有 |
|---|---|
| `next_action` | 重启后第一眼要知道做什么 |
| `blocked_by` | 卡在哪一环（封禁/缺账号/缺出口），避免下次原地重试 |
| `hypotheses[].state` | 三态归零（§27）：未决/证实/排除 |
| `budget.used` | 已花多少请求，防超预算 |
| `tested[]` | 试过什么，防止重复劳动 |

### 33.4 与台账、账本的区别

| 存什么 | 在哪 |
|---|---|
| 授权范围、账号 | 桌面 `域名信息汇总表.xlsx` |

## 34. 改动必须实测生效：不许"改完就当成了"（2026-11-19 用户定）

**用户原话**：「你经常出现改动后，不生效然后自检发现有问题的情况，或许在这一方面，你也需要增加一个独立复核 Validator，
或是把这部分交给它，改进完后必须实测，记住！！！」

**已发生的事故（同一个病，反复发作，明细见 `runs/notes/改动失效案例.md`）**：
进程内旧模块被当成代码 bug 查了 4 次 ｜ `DEFAULT_PROMPTS` 改了不重启 ｜
角色提示词"必须"二字缺失 ｜ 本轮 `verify_change.py` 连挂两次（进程名错、PowerShell 返回中文日期）。

**根因**：我验证的是"文件改了吗"，而真正要验证的是"**运行时读到的是不是新版**"。

### 34.1 五层验证（缺一层就是没验证完）

| 层 | 验什么 | 怎么验 | 失败后果 |
|---|---|---|---|
| L1 存在 | 文件在不在、大小 | `ls` / `verify_change.py file` | 白改 |
| L2 语法 | 能不能加载 | `py_compile` / `node --check` / `json.load` | 整个模块挂掉 |
| L3 内容 | 关键串在不在 | `grep` 精确串（**不凭印象**） | 改了但改错位置 |
| L4 **生效方式** | 立即生效 还是 需重启 | `verify_change.py file <路径>` 会判断 | **这就是我反复踩的坑** |
| L5 **运行时行为** | 实际调用返回的对不对 | 真跑一次命令/工具 | 工具本身是坏的 |

**L4 是分水岭**：
- **立即生效**（读文件型）：`AGENTS.md`、`技能 *.md`、`派活模板`、`runs/tools/*.py` —— 改完即生效，但必须做 L3
- **需重启**（进程内/启动时加载）：插件 `lib/*.js`、`cordis.patch.yml`、`presets/*.yml`、`DEFAULT_PROMPTS`、各靶标 `agents/*.md`
  —— **改完不重启 = 没改**

### 34.2 工具：`runs/tools/verify_change.py`

```bash
# ★ 每次改完必跑：列出"启动后被修改的进程内文件"= 很可能没生效
"$PY" runs/tools/verify_change.py restart

# 单文件五层检查
"$PY" runs/tools/verify_change.py file AGENTS.md --must-contain "## 34." 
"$PY" runs/tools/verify_change.py file runs/tools/state.py --syntax py --must-contain "def cmd_why"

# 技能可加载性
"$PY" runs/tools/verify_change.py skill finding-review --must-contain "独立复核"

# 关键载体冒烟
"$PY" runs/tools/verify_change.py all
```

**重启后必须再跑一次 `restart`，看到 ✅ 才算完。**

### 34.3 反向测试原则 ★

**验证工具本身时，必须证明"它能报错"，不能只测正常路径。**
一个永远返回"✅ 没问题"的工具，比没有工具更坏——它制造虚假的安全感。

做法：
1. 先测正常态 → 应 ✅
2. **故意制造一个应当被抓到的问题**（比如 `os.utime` 把某个模块文件时间戳改成现在）
3. 确认工具真的报出来了
4. 恢复现场，再测一次 → 回到 ✅

**本轮实际执行过**：touch `node_modules/.../validate.js` → `restart` 准确列出 2 个文件（node_modules + vendor） → 恢复 mtime → 回到 ✅。

### 34.4 重大改动交给独立复核

**载体级改动**（AGENTS / DEFAULT_PROMPTS / 技能判据 / 派活模板）改完后，除了自己跑 `verify_change.py`，
还要**派一个独立 agent 验收**——它不看我的结论，自己去读文件、跑命令，回报"实际读到什么"。

判定：它读到的关键串和我要的一致 → 通过；不一致或读不到 → 我改错了地方。

**理由**：我验自己改的东西会有确认偏差（"我记得改了"），独立 agent 没有。

### 34.5 一句话规矩

> **改完没跑 `verify_change.py`，等于没改。跑了看到 ⚠️ 没重启，等于白改。**

### 34.6 规则库没有上限，减负叫后勤

**不设字符上限**——文件随使用增长是正常的，卡上限等于逼自己删掉有用的规则去腾地方（2026-11-19 用户否掉了我最初的做法）。

- **平时**：`verify_change.py budget` 只看**趋势**（比上次涨/降多少）+ **重复长句** + **失效引用**，不判超限。
- **要减负时**：用户说「后勤减负」→ 加载技能 `logistics-maintenance` → 体检 → 出清单 → **等确认** → 搬迁
  （挪进技能 / 归档 notes，**不是删**）。
- **默认归档，不默认删除**：内容挪走后需要时 `skill` 还能加载，信息一点不少；只有被后续规则推翻的才真删。
- 新增规则前仍先判一句「每轮都要生效吗」：是 → AGENTS；只在特定场景 → 技能。
